## 1. 第八步遗留问题：同 Prefix 并发重复 Load

第八步 Async Load 解决了 HoL 阻塞与 compute/load 重叠，但在**同 Prefix 并发 CPU HIT** 的 load-bound 工作负载上，async 总墙钟反而**略高于 sync**（§38：n=4 sync 1315ms vs async 1444ms，n=8 sync 1327ms vs async 1455ms，async 慢 ~8–10%）。

根因（第八步报告 §38 已如实记录）：同 prefix 同 batch + `reset_l1_cache` 下——
1. **sync**：请求 1 同步 load 后**立即 commit 到 L1**，请求 2..N 变 L1 hit（免 CPU load），全程仅 **1 次** CPU load。
2. **async**：请求 1/2 进 LOAD_PENDING（**延迟 commit**），L1 promotion 推迟，请求 3 需 sync fallback load、更多请求走 CPU load 路径——async 做了更多总 load 工作（`max_pending=2` 下 2 pending + 1 fallback ≈ **3 次** vs sync 1 次）。
3. 每 step `poll_load_completions` 的 event.query 开销在 N 个请求多轮 step 上累积。

**本质**：async 的"延迟 L1 promotion"在 load-bound 同 prefix 场景是劣势——sync 的"阻塞"反而因快速 promote 到 L1 而让后续请求免费复用。async 的价值在 HoL + overlap，不在 load-bound 同 prefix 吞吐。

第九步要做的，正是**让 async 在同 prefix 场景也只做 1 次 load**：同 Prefix 并发的后续 Request 不再各自独立 submit，而是 join 一个共享 group，owner 做 1 次 H2D，完成后 1 次 L1 promote，所有 waiter 共享同一组 MLU physical blocks。

---

## 2. 第九步总体架构

```
同 Prefix 并发 CPU HIT (L1 MISS, L2 HIT)
→ 第 1 个 Request = owner:
    L2 lookup -> reserve MLU target -> acquire CPU refs -> acquire staging
    -> async H2D+unpack -> record Event -> LOAD_PENDING
    -> 创建 PendingLoadGroup(key, owner, waiters=[]) -> pending_prefix_loads[key]=group
→ 第 2..N 个 Request = waiter (相同 PendingPrefixKey):
    L2 lookup 命中同一组 -> 查 pending_prefix_loads[key] -> group.state==LOADING
    -> join group.waiters (不 reserve target, 不 acquire refs, 不占 staging, 不 H2D)
    -> LOAD_PENDING (WAITING_FOR_SHARED_LOAD)
→ Scheduler 不阻塞, 继续处理其他 ready seq
→ Event complete (owner):
    commit_cpu_hit (注册 hash->target MLU block 到 L1, 1 次 promote)
    -> group.state=READY, 从 pending_prefix_loads 删除
    -> owner 回 waiting
    -> 所有 waiter 回 waiting (§八: 下次 schedule 走正常 L1 lookup, 共享刚 promote 的 physical blocks)
→ 后续 step: owner+waiters 全部 L1 HIT (ref_count++ 共享), 0 次 CPU load
```

三个机制叠加：
- **A. Pending Load Coalescing**：同 Prefix 在 LOAD_PENDING 时只 1 个 owner 真实 H2D，其余 join waiter（§三~§六）。
- **B. Shared L1 Promotion**：owner 完成后 1 次 L1 promote，waiter 经 L1 lookup 共享同一组 MLU physical blocks（ref_count 反映共享，§七/§八/§十二）。
- **C. Adaptive Sync/Async Policy**：单请求无重叠 compute 时选 sync（立即 promote，省 pending/poll）；有重叠 compute 时选 async（保留 HoL/overlap，§十四/§十五）。

## 3. Coalescing Key（PendingPrefixKey）

`PendingPrefixKey = (l1_hit: int, l2_hit: int, last_hash: int)`（`scheduler.py:25`）。
唯一表达"同一份正在从 CPU 提升到 MLU 的 Prefix"。nanoLLM 的 block hash 是链式：`hash_i = H(hash_{i-1}, block_tokens_i)`，故 `hash_i` 已编码 `[0..i]` 全部 token。两个 Request 的 L2 命中段"完全相同"（§十：只做 full-match coalescing，不做 sub-prefix）当且仅当：
- `l1_hit` 相同（L1 命中数相同），
- `l2_hit` 相同（L2 命中数相同），
- `last_hash` 相同（L2 命中段末块 hash 相同）。

依据：group LOAD_PENDING 期间其 L2 块**尚未注册进 `hash_to_block_id`**（commit 才注册），故同一 prefix 的后续 Request 看到的 L1 状态与 owner 完全一致（`l1_hit` 稳定），L2 lookup 命中同一组受 refcount 保护的 CPU 块（`l2_hit`/`l2_hashes` 稳定）。**不用 request_id / seq_id**（§三）。

构造：`_make_prefix_key(l1_hit, l2_hashes)` → `(l1_hit, len(l2_hashes), l2_hashes[-1] if l2_hashes else -1)`（`scheduler.py:156-166`）。

## 4. PendingLoadGroup

`PendingLoadGroup` dataclass（`scheduler.py:28-50`）——一份正在从 CPU 提升到 MLU 的 Prefix：

| 字段 | 含义 |
|---|---|
| `group_id` | 单调递增 id |
| `key` | PendingPrefixKey |
| `l1_hit` / `l2_hit` | 命中块数 |
| `block_hashes` | L2 命中块链式 hash（供 commit 注册 L1） |
| `cpu_block_ids` | 源 CPU block id（owner 独占 acquire refs） |
| `l2_token_blocks` | L2 命中块各自 token_ids（供 commit 校验） |
| `owner_seq_id` | owner 的 seq_id |
| `target_mlu_block_ids` | 目标 MLU physical block id（owner 独占 reserve） |
| `num_blocks` | L2 命中块数 |
| `load_job_id` | owner 的 AsyncLoadJob id |
| `state` | `LOADING` / `READY` / `FAILED` |
| `waiters` | `list[Sequence]`（join 的 waiter） |
Owner 持有全部 IO 资源（AsyncLoadJob + target MLU reservation + CPU refs + staging）；Waiter **只**加入 `group.waiters`，不持有任何 IO 资源（§六）。`AsyncLoadJob` 仍是底层 IO Job；`PendingLoadGroup` 是 Scheduler/Cache 语义层。

全局 pending map：`pending_prefix_loads: dict[PendingPrefixKey, PendingLoadGroup]`（`scheduler.py:83`）。同 Prefix 并发时，第一个 Request 创建 group（owner）并真实 H2D；后续相同 Prefix Request join waiter（§五/§六），不重复 H2D。

## 5. Owner / Waiter 语义

**Owner**（`_submit_owner_load`，`scheduler.py:171-253`）：真实 submit async load + 创建 PendingLoadGroup。`acquire_load_refs` → `submit_load` → 成功则创建 group、`pending_prefix_loads[key]=group`、`record_coalesce_group_created`、`record_policy_decision(is_async=True)`；失败（`too_large`/`staging_busy`）则 sync fallback（复用已 reserve 的 target blocks），`load_io_failure` 则 rollback。

**Waiter**（`_join_waiter`，`scheduler.py:255-273`）：`group.waiters.append(seq)`、`record_coalesce_waiter_joined`、更新 `cpu_load_waiters_current`/`pending_prefix_groups`。**不 acquire CPU refs，不 reserve target MLU blocks，不占 staging，不 H2D**。seq 进 LOAD_PENDING（`WAITING_FOR_SHARED_LOAD`），等 group promotion complete 后回 waiting 走正常 L1 lookup 共享 physical blocks。

**统一入口**（`_try_cpu_load`，`scheduler.py:535-625`）：第九步统一 CPU HIT 处理，查询顺序 L1 → Pending → L2 → Prefill（§九）：
1. L1 MLU Prefix Cache（调用方 `can_allocate` 给出 `l1_hit`）
2. Pending Prefix Promotion Map：若已有相同 pending group 且 `state==LOADING` → join waiter
3. L2 CPU Prefix Cache lookup
4. L2 HIT → adaptive policy 决定 sync / async
   - sync：同步 Load + 立即 promote L1（§十四 场景A，`_sync_load_and_commit`）
   - async：owner submit + 创建 PendingLoadGroup（coalescing 启用时，`_submit_owner_load`）
5. L2 MISS → 走原 prefill

Coalescing 关闭（`cpu_prefix_load_coalesce=False`）时退回第八步逐 Request 独立 async load（`_try_async_cpu_load_inner`，不查 pending map，不 join waiter）。

## 6. Shared L1 Promotion

Owner Event complete 后（`_complete_pending_load` → `_resolve_group_on_owner_done`，`scheduler.py:729-835`）：
- `commit_cpu_hit` 注册 `hash -> target MLU block` 到 L1（**1 次** promote，`block_manager.py:210-219`）。
- `group.state = "READY"`，从 `pending_prefix_loads` 删除。
- `record_shared_prefix_promote(num_blocks, num_blocks * num_waiters)`：`mlu_shared_prefix_blocks += num_blocks`，`mlu_duplicate_prefix_blocks_avoided += num_blocks * num_waiters`，`mlu_prefix_memory_saved_mb += duplicate_avoided * 2.25`（§十三）。
- owner 回 waiting。
- **所有 waiter 回 waiting**（§八：`waiting.appendleft`，下次 schedule 走正常 L1 lookup 共享）。

**Waiter 共享机制（§八）**：waiter **不**手工批量写 `block_table`、**不**手工 reserve target blocks。owner commit 后 waiter 回 waiting，下一次 `schedule()` 走正常 `can_allocate` → L1 lookup，命中刚 promote 的 hash，`allocate_prefix` 的 L1 命中循环对 shared physical block `ref_count++`（`block_manager.py:165-176`）。共享是经 L1 自然发生的，无额外代码路径。

## 7. Adaptive Sync/Async Policy

`_decide_load_policy(current_seq)`（`scheduler.py:137-151`）：
- `always_sync` → `"sync"`
- `always_async` → `"async"`
- `adaptive` → `_has_other_ready_compute(current_seq)` ? `"async"` : `"sync"`

`_has_other_ready_compute`（`scheduler.py:119-135`）：低开销判断（不做 dry-run schedule）——
- `running` 中有 decode-ready seq（任一 running 都可继续 decode）→ True
- `waiting` 中除 `current_seq` 外还有可处理 seq（`block_table` 已就绪，或可 cold prefill）→ True
- 否则 False

典型行为（§十六）：
- **单 CPU HIT 请求**（无其他 ready compute）→ **sync**：立即 Load + promote L1，省 pending/poll 开销，后续相同 Prefix 直接 L1 HIT。
- **CPU HIT A + cold/L1-hit B**（有重叠 compute）→ **async**：A 进 LOAD_PENDING，B 立即 compute，load 在 transfer_stream 后台与 compute 重叠，保留 HoL 消除 + overlap。
- **同 Prefix 并发**（A/B/C/D 同 prefix）→ 第一个 owner async（若有其他 ready）或 sync（若独占），其余 join waiter，**无论 sync/async，load count 都 = 1**（§三十，最重要 invariant）。

---

## 8. CPU Refcount / Shared MLU Refcount

**CPU refcount**（§十一）：只 owner `acquire_load_refs`（submit 前），waiter **不** +1。Event complete/fail 后 owner `release_load_refs`。`pop_lru_evictable` 跳过 ref>0 的 CPU block，防 H2D 期间被 LRU 淘汰。waiter 不持有 CPU refs——它不读 CPU block，只等 owner 的 MLU promote。
**Shared MLU refcount**（§十二）：owner commit 后 target MLU blocks 注册进 L1（`ref_count=1`，由 `_allocate_block` 设）。waiter 回 waiting 后经 L1 lookup 命中同一 hash，`allocate_prefix` L1 命中循环 `ref_count++`。N 个 seq 共享同一组 physical blocks，`ref_count = N`。完成后 `deallocate` 逐个 `ref_count--`，归 0 才真正释放。测试 §23 验证：4 req 共享，`ref_count=4`，完成后归 0。

---

## 9. MLU KV Memory Savings

`record_shared_prefix_promote(shared_blocks, duplicate_avoided)`（`prefix_cache_backend.py:473-482`）：
- `shared_blocks = num_blocks`（实际只保留一份的 prefix MLU blocks）
- `duplicate_avoided = num_blocks * num_waiters`（waiter 本会各占一份重复 KV，现共享同一份）
- `mlu_prefix_memory_saved_mb += duplicate_avoided * 2.25`（单 block ≈ 2.25MB）

基准 §36（4096 shared prefix，256 blocks）：

| n | unique blocks | saved blocks | saved MB |
|---|---|---|---|
| 2 | 256 | 256 | 576.0 |
| 4 | 256 | 768 | 1728.0 |
| 8 | 256 | 1792 | 4032.0 |

n=8 时 8 个请求本需 8×256=2048 份 prefix MLU blocks（≈4.6GB），coalescing 后只 256 份（≈576MB），**节省 4032MB**。

## 13. §38 回归消除的机制解释

为什么 coalescing 让 async 在同 prefix 场景追上 sync？

| | sync | always_async（第八步） | async_coalesce（第九步） |
|---|---|---|---|
| H2D 次数 | 1（请求1 sync load，2..N L1 hit） | 3（2 pending + 1 fallback，`max_pending=2`） | **1**（owner，waiter 不 H2D） |
| L1 promote 时机 | 立即（请求1） | 延迟（Event complete） | 延迟（owner Event complete），但**只 1 次** |
| 后续请求路径 | L1 hit（免 load） | 部分 L1 hit + 部分 CPU load | 全部 L1 hit（共享 promote） |
| avg_ttft | 低（193/200） | 高（320/330，延迟 promote） | 低（194/205，共享 promote 后 L1 hit） |

always_async 的劣势来自"延迟 promote + 多次 load"双重开销；coalescing 把"多次 load"压到 1 次，waiter 经共享 promote 全部 L1 hit，avg_ttft 回到 sync 水平。延迟 promote 的 1 次 overhead 被"只 1 次 load"抵消，总墙钟持平 sync。
7）。
- **throughput**：n=8 adaptive_coalesce 6.02 ≈ sync 6.03，always_async 仅 5.13。同 prefix load-bound 吞吐回归**消除**。

## 13. §38 回归消除的机制解释

为什么 coalescing 让 async 在同 prefix 场景追上 sync？

| | sync | always_async（第八步） | async_coalesce（第九步） |
|---|---|---|---|
| H2D 次数 | 1（请求1 sync load，2..N L1 hit） | 3（2 pending + 1 fallback，`max_pending=2`） | **1**（owner，waiter 不 H2D） |
| L1 promote 时机 | 立即（请求1） | 延迟（Event complete） | 延迟（owner Event complete），但**只 1 次** |
| 后续请求路径 | L1 hit（免 load） | 部分 L1 hit + 部分 CPU load | 全部 L1 hit（共享 promote） |
| avg_ttft | 低（193/200） | 高（320/330，延迟 promote） | 低（194/205，共享 promote 后 L1 hit） |

always_async 的劣势来自"延迟 promote + 多次 load"双重开销；coalescing 把"多次 load"压到 1 次，waiter 经共享 promote 全部 L1 hit，avg_ttft 回到 sync 水平。延迟 promote 的 1 次 overhead 被"只 1 次 load"抵消，总墙钟持平 sync。
adaptive_coalesce 进一步在"无重叠 compute"时选 sync（单请求场景），在"有重叠 compute"时选 async（保留 overlap），是 async_coalesce 的严格改进（n=8 total 1328 vs 1336，因 n=8 首个请求 adaptive 选 sync 立即 promote，省 1 轮 pending）。

## 14. 限制与设计取舍

1. **只 full-match coalescing，无 sub-prefix**（§十）：key 含 `l1_hit`/`l2_hit`/`last_hash`，只有 L2 命中段完全相同的 Request 才 coalesce。prefix A 是 prefix B 的前缀但 B 更长 → 不同 key，不 coalesce（B 的 owner 独立 load 其额外段）。这是有意的：sub-prefix coalescing 需部分 promote + 部分等待，复杂度大且收益小。
2. **max_pending=2 不变**：coalescing 已把同 prefix 的 H2D 压到 1 次，`max_pending` 限制对同 prefix 不再是瓶颈；不同 prefix 仍受 2 slot 限制（超则 sync fallback，不丢缓存）。
3. **waiter 经 L1 共享，不手工写 block_table**（§八）：owner commit 后 waiter 回 waiting 走正常 L1 lookup。若 owner fail，waiter 回 waiting 走 L1→L2→Prefill（可能各自重新 load 或 coalesce 新 group），无丢失。
4. **adaptive 依赖 `_has_other_ready_compute` 的低开销启发式**：不 dry-run schedule，只查 `running`/`waiting` 非空。极端边界（如 waiting 中只有 LOAD_PENDING seq）可能误判，但 fallback 安全（sync 不破坏正确性）。
5. **Coalescing group 生命周期与 Event 绑定**：owner Event complete/fail 才 resolve group。owner 取消（cancel_load_job）也触发 resolve（`success=False`，waiter 回 waiting）。
6. **pre-existing async_store exact-match 问题**（§11 已述）：非第九步引入，超出 §一 范围。

## 15. 14 个问题回答

1. **为什么同 Prefix 并发会重复 Load？** 第八步每个 CPU HIT Request 独立走 `_try_async_cpu_load`：各自 L2 lookup 命中同一组 CPU 块、各自 acquire refs、各自 reserve 不同 target MLU blocks、各自 submit H2D。`max_pending=2` 下前 2 进 LOAD_PENDING，第 3+ 因 staging_busy sync fallback。结果：N 个同 prefix 请求产生 ~3 次 H2D（2 async + 1 sync fallback），且延迟 L1 promotion 使后续请求无法免费 L1 hit。根因是"无共享语义"——每个 Request 不知道已有相同 prefix 在 load。
2. **Coalescing Key 为什么是 (l1_hit, l2_hit, last_hash)？** 链式 hash `hash_i = H(hash_{i-1}, ...)` 使末块 hash 编码 `[0..i]` 全部 token。两 Request 的 L2 命中段"完全相同"当且仅当 `l1_hit`（L1 前缀相同）、`l2_hit`（L2 段长度相同）、`last_hash`（L2 段末块相同）三者一致。group LOAD_PENDING 期间 L2 块未注册 L1，后续 Request 看到的 L1 状态与 owner 一致（`l1_hit` 稳定），故 key 稳定。不用 seq_id（与具体 Request 无关，只与 prefix 内容有关）。

3. **Owner 和 Waiter 各持有什么资源？** Owner 持有 AsyncLoadJob + target MLU reservation（block_table 已写）+ CPU refs（acquire）+ staging slot。Waiter **什么都不持有**——只 `group.waiters.append(seq)`。这是关键：waiter 零 IO 资源，owner 失败时只需 resolve group（waiter 回 waiting），无需释放 waiter 的任何资源。

4. **Waiter 如何共享 MLU Prefix Blocks？** 不手工写 block_table。owner commit 后 `commit_cpu_hit` 注册 hash→target MLU block 到 L1（1 次 promote）。waiter 回 waiting 后下次 `schedule()` 走 `can_allocate` → L1 lookup 命中同一 hash → `allocate_prefix` L1 命中循环对 shared block `ref_count++`。共享经 L1 自然发生，N 个 seq 共享同一组 physical blocks，`ref_count=N`。

5. **为什么只做 full-match coalescing，不做 sub-prefix？** sub-prefix（A 是 B 前缀）需部分 promote + 部分等待 + 共享前缀段独立 load 后缀段，复杂度大；且实际 workload 中同 prefix 并发远多于 sub-prefix 并发。key 含 `l2_hit` 保证只 coalesce 完全相同的 L2 命中段，简单且覆盖主要场景。

6. **Adaptive policy 如何决定 sync/async？** `_decide_load_policy`：`always_sync`→sync，`always_async`→async，`adaptive`→`_has_other_ready_compute` ? async : sync。`_has_other_ready_compute` 查 `running` 非空或 `waiting` 有其他可调度 seq。单请求无重叠→sync（立即 promote，省 pending/poll）；有重叠 compute→async（保留 HoL/overlap）。
7. **`_has_other_ready_compute` 的判断依据是什么？** 低开销启发式，不 dry-run schedule：(1) `running` 中有 seq（任一都可继续 decode）→ True；(2) `waiting` 中除 current_seq 外有 `block_table` 已就绪或 `num_tokens>0`（可 cold prefill）的 seq → True。不精确（不检查 can_allocate），但 fallback 安全——误判选 sync 不破坏正确性，只是少一次 overlap 机会。

8. **同 Prefix 并发时无论 sync/async load count 为什么都是 1？** sync：请求1 sync load + 立即 promote L1，请求2..N L1 hit（免 load）→ 1 次。async+coalesce：请求1 owner async load，请求2..N join waiter（不 H2D），owner complete 后 1 次 promote，waiter L1 hit → 1 次。两条路径都因"1 次 promote + 后续 L1 hit"而 load count=1。这是 §三十最重要 invariant，测试 §24/§30/§36 全部验证 `h2d_load_jobs==1`。

9. **Owner Load 失败时 Waiter 如何恢复？** `_resolve_group_on_owner_done(success=False)`：`group.state=FAILED`，从 `pending_prefix_loads` 删除，所有 waiter 回 waiting（`waiting.appendleft`）。waiter 下次 schedule 走 L1→L2→Prefill：L1 miss（owner 未 commit）、L2 仍命中（CPU 块未被淘汰，owner fail 已 release refs）→ 各自重新 load 或 coalesce 新 group。无丢失（测试 §26 验证 owner+waiter 全回 waiting 且全部完成）。

10. **Waiter 取消会影响 Owner 的共享 IO 吗？** waiter 不持有 IO 资源，取消（从 `group.waiters` 移除）不影响 owner 的 AsyncLoadJob/CPU refs/staging/target。owner 独立完成 promote，剩余 waiter 仍共享。owner 取消（`cancel_load_job`）则触发 resolve `success=False`，所有 waiter 回 waiting。

11. **PendingLoadGroup 与 AsyncLoadJob 的关系？** AsyncLoadJob 是底层 IO Job（H2D+unpack+Event，第八步已有）；PendingLoadGroup 是 Scheduler/Cache 语义层，包装 owner 的 job + waiter 列表 + 共享元数据。一个 group 对应一个 owner job（`load_job_id`）；waiter 无 job。group resolved（commit/fail）后从 `pending_prefix_loads` 删除，job 由 `_complete_load_job`/`_fail_load_job` 释放。

12. **Coalescing 如何节省 MLU KV 内存？** 无 coalescing：N 个同 prefix 请求各 reserve N 组 target MLU blocks（各 256 blocks @4096），N×256 份 prefix KV。coalescing：owner reserve 1 组，waiter 不 reserve（等 L1 共享），promote 后全部经 L1 hit 共享同一组 256 blocks。节省 (N-1)×256 blocks = (N-1)×576MB。n=8 节省 4032MB（测试 §25 + 基准 §36 验证）。
13. **Coalescing 是否破坏 HoL 消除或 overlap？** 不破坏。HoL：adaptive+coalesce 仍 19.67ms reduction（vs 第八步 20.24ms，未退化）——owner async 时 B cold compute 仍立即进 batch。overlap：0.822（vs 0.777，未退化）——单 load 的 H2D+unpack 仍在 transfer_stream 与默认流 compute 重叠。coalescing 只减少 H2D 次数，不改变单次 load 的 overlap 路径。

14. **第九步是否达成目标？当前限制？** 达成：同 prefix 并发 load count=1（§30 invariant）、1 次 L1 promote、waiter 共享 MLU blocks、MLU KV 内存显著节省（n=8 省 4032MB）、§38 同 prefix async 回归消除（async_coalesce/adaptive_coalesce 持平 sync）、HoL/overlap 未退化、135 测试 + 全回归 PASS、0 invariant 违反。限制：只 full-match 无 sub-prefix、adaptive 启发式不精确（fallback 安全）、max_pending=2 对不同 prefix 仍限制、pre-existing async_store exact-match 问题（非本步引入）。

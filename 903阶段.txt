# Coalescing + Adaptive Load Policy 报告 (INT8 KV + FP32 Scale)

**阶段**: Prefix KV Offload 下一阶段 —— Stream Dependency Hardening (P0) + Pending Load Coalescing (P1) + Adaptive Sync/Async Load Policy (P2)
**平台**: MLU590-M9DG 80GB, torch_mlu 1.31.1 + torch 2.9.1, Qwen3-8B bf16, TP=1
**量化路径**: INT8 KV + FP32 Scale (单一 allocator, 单 Event, 同 transfer_stream), 容量 1.9394x
**日期**: 2026-08-24

---

## §1 任务范围与约束

本阶段在已完成的 Quantized Hierarchical Prefix Cache (Step 1-9) 基础上, 实现三项硬化:

- **P0 Stream Dependency Hardening**: KV/Scale 生产者 (default/compute stream) 与 pack (pack_stream/transfer_stream) 之间无隐式同步, pack 可能读到 stale/partial KV/Scale。原热路径用 `torch.mlu.synchronize()` (device-wide barrier) 兜底。目标: producer stream `record Event` → transfer/pack stream `wait_event` → pack → D2H, **热路径禁止 device-wide sync**。
- **P1 Pending Load Coalescing**: 同 CPU prefix 并发请求, 首个 Load 未完成时后续请求重复 H2D/staging/MLU block。目标: `PendingPrefixKey` (matched block hashes, 非 request_id) + `PendingLoadGroup` (owner 持全部 IO, waiter 持 0), 单次 CPU→MLU promotion, 共享 MLU physical blocks, CPU refcount=1 (Step 9 已实现, 本阶段补量化测试)。
- **P2 Adaptive Sync/Async Load Policy**: `cpu_prefix_load_policy` = always_sync / always_async / adaptive。adaptive: 同 prefix 已 pending → join waiter; elif 有其他 ready compute → async; else → sync (Step 9 已实现, 本阶段验证量化路径)。

**严格约束 (verbatim, 全程遵守)**:
- 禁止: Active KV Offload, ARC, SSD/L3, INT4/FP8, speculative decoding, Attention Kernel/torch_mlu_ops 修改, CNRT C++ extension, 大规模 Scheduler 重构, 重写 Prefix Hash/LRU, 修改 Quantized CPU L2 layout。
- 允许: producer-ready Event/stream wait, 修改必要的 Async Store/Load stream 依赖, PendingPrefixKey/PendingLoadGroup, owner/waiter 语义, 最小必要 Scheduler 改动, adaptive load policy, metrics/tests/benchmark。
- **停止条件达成后不再继续** (不进入 Active KV Offload / ARC / SSD / INT4 / FP8 / CNRT C++ / speculative decoding)。

## §2 P0 实现概述

### 2.1 Mover 层 (producer_event 跨流依赖)

`QuantizedKVBlockMover` 与 `KVBlockMoverV2` 的 `pack_to_staging` / `store` 新增 `producer_event=None` 参数:

```python
def pack_to_staging(self, staging_kv, staging_scale, mlu_block_ids,
                    pack_method="A", producer_event=None):
    with torch.mlu.stream(self.pack_stream):
        if producer_event is not None:
            self.pack_stream.wait_event(producer_event)  # pack 等生产者写完成
        self.pack_kv(staging_kv, mlu_block_ids, pack_method)
        self.pack_scale(staging_scale, mlu_block_ids, pack_method)
    self.pack_stream.synchronize()  # stream-local, 只等 pack
```

`producer_event` 由 scheduler 在 default/compute stream 上 record (forward 写 KV 之后), pack_stream `wait_event` 建立跨流依赖 (不阻塞 host, 不需 device-wide sync)。`None` = 调用方已保证 source ready (兼容旧测试)。

### 2.2 Backend 层 (producer_event 透传 + metrics)

`PrefixCacheBackend.submit_store` / `store_blocks` 新增 `producer_event` 参数, 透传到 mover, 并递增 `stream_dependency_waits` 计数。

### 2.3 Scheduler 层 (record producer_event + 移除热路径 device sync)

`postprocess` 在 `seq.status = FINISHED` 后、store/deallocate 前:
```python
producer_event = None
if self.cpu_prefix is not None:
    producer_event = torch.mlu.Event()
    producer_event.record()  # default/compute stream, forward 写 KV 之后
    self.cpu_prefix.metrics.stream_dependency_events_recorded += 1
if self.cpu_prefix is not None and getattr(self.cpu_prefix, "async_store_enabled", False):
    self._submit_store_to_cpu(seq, producer_event=producer_event)
else:
    self._store_to_cpu(seq, producer_event=producer_event)
```

**移除全部 5 处热路径 `torch.mlu.synchronize()`** (原 lines 236/288/373/509/674), 改依赖 mover 内部 `transfer_stream.synchronize()` (sync load, stream-local) 或 Event complete (async load)。AST 验证: 0 个可执行 `torch.mlu.synchronize()` Expr 语句残留 (仅 docstring 文本提及)。

### 2.4 Metrics

`CacheMetrics` 新增:
- `stream_dependency_events_recorded`: producer_event record 次数
- `stream_dependency_waits`: pack wait_event 次数
- `device_wide_sync_hotpath_count`: 热路径 device-wide sync 次数 (应恒为 0)

## §3 MLU590 跨流可见性实证结论 (P0 设计依据)

为 P0 设计提供实证基础 (详见 memory [[mlu-stream-visibility-2026-08]]):
1. **P0 producer→transfer 竞争真实存在**: default stream 写 KV/Scale + heavy compute, transfer_stream 无 wait_event 直接 pack 读 → INT8 **299/300 stale**。加 `producer_event.record()` + `wait_event` → **0/300**。验证 P0 必需。
2. **`transfer_stream.synchronize()` (stream-local) 足够供 default stream 后续读**: INT8 store+load round-trip, 仅 stream-local sync, default 读目标块 → **0/300** (含 heavy concurrent default compute)。热路径 device-wide `torch.mlu.synchronize()` 冗余, 可移除。前提: 目标块 unique per job (真实系统 `allocate_prefix` 保证)。
3. **`event.query()=True` 不足以保证 default stream 可见性** (async load poll 路径): 但真实 async load 路径中, commit 后 seq 回 waiting, 下一 step 的 schedule 在 default stream 跑 prefill —— transfer_stream 写早已完成且 `transfer_stream.synchronize` 在 submit 时已建立顺序。实测 INT8 **0/300**。安全。
4. **bf16 精度伪影**: `float(257) → bf16 → 256.0` (7-bit mantissa 截断)。早期 22/300 "mismatch" 全是 bf16 精度, 非 sync bug。跨流可见性测试禁用 bf16 uniform 值, 用 int8 或 distinguishable values。
5. **torch.mlu.Event/wait_event API**: `ev.record()` 在当前流; `stream.wait_event(ev)` 建跨流依赖 (consumer 等 producer); 跨流依赖不阻塞 host, 不需 device-wide sync。

## §4 §一~§八 Stream Dependency 分析问题回答

**§一 为什么 default stream 写 KV/Scale 后, transfer_stream 的 pack 可能读到 stale/partial 数据?**
MLU stream 间无隐式同步。default stream (forward/compute) 写 KV/Scale 与 transfer_stream (pack) 读 source 是两个独立 stream, 无依赖时 pack 可在 forward 写完成前执行, 读到未完成或被后续覆盖的数据。

**§二 producer_event 必须在什么位置 record?**
必须在**最后一次会修改即将 offload 的 KV/Scale 写之后**。本实现: `postprocess` 中, `run_model` (forward, 写 KV) 已由 `LLMEngine.step` 在 `postprocess` 之前调用完成, 此时 record 在 default/compute stream, 覆盖 forward 的全部 KV/Scale 写。
**§三 为什么 pack_stream.wait_event(producer_event) 而非 transfer_stream.wait_event?**
pack 在 pack_stream 执行 (Async Store 分流: pack 用 pack_stream, D2H 用 transfer_stream, 避免 Job B 的 pack 被 Job A 的 D2H 阻塞)。wait_event 必须在执行 pack 的 stream 上, 让 pack 等生产者写。sync `store` 路径 pack+D2H 同在 transfer_stream, 故 wait_event 在 transfer_stream。

**§四 为什么不需要 device-wide torch.mlu.synchronize()?**
producer_event + wait_event 建立精确的跨流依赖 (pack 只等 forward 写, 不等其他 stream 的无关工作)。device-wide sync 会阻塞 host 等待 ALL streams (含并发 compute / in-flight D2H), 引入 ms 级 host 阻塞。stream-local `pack_stream.synchronize()` / `transfer_stream.synchronize()` 只等本 stream 的 pack/D2H, 不等无关工作。

**§五 store source 生命周期: submit 返回后 source MLU blocks 可否立即释放/覆盖?**
可以。`pack_to_staging` 内 `pack_stream.synchronize()` 保证 pack 已完成 (source 已读进独占 staging), D2H 只依赖 staging 不再读 source。故 `submit_store` 返回 → `deallocate(seq)` 安全。实证 §8: submit 后立即覆盖 source KV+Scale, D2H 仍 bit-exact。

**§六 async load 的 consumer (下 step prefill) 何时可见 target blocks?**
Event record 在 unpack 之后 (transfer_stream)。poll `event.query()=True` → commit → seq 回 waiting → 下一 step schedule 在 default stream 跑 prefill。此时 transfer_stream 的写 (H2D+unpack) 早已完成 (Event complete 蕴含), 且 submit 时 `transfer_stream.synchronize` 已建立顺序。default stream prefill 读 target 可见。实证 INT8 0/300。

**§七 producer_event 失败 (record/wait 异常) 如何处理?**
record/wait_event 是 host API, 失败抛异常。`submit_store` 的 pack 在 try/except 中, 异常 → `_rollback_submit` (释放 pending hash / CPU block / staging slot), 返回 `store_io_failure`。scheduler 对 `store_io_failure` fallback 同步 `_store_to_cpu`。不污染状态。

**§八 移除热路径 device-wide sync 后, 哪些不变量仍成立?**
- store source 生命周期: pack wait_event 保证 pack 读完整 source, submit 返回可 deallocate (§5 实证)。
- load consumer 可见性: Event complete + 下 step default prefill, transfer_stream 写已完成 (§6 实证)。
- bit-exact: INT8 KV + FP32 Scale round-trip 0 mismatch (§3 实证, §1/§4 测试)。
- 无悬挂 ref / staging / pending: invariant_ok 持续 (全部回归 + 5000-op 压力)。

## §5 P1 Pending Load Coalescing 实现回顾 (Step 9, 本阶段量化验证)

- `PendingPrefixKey` = (l1_hit, l2_hit, last_hash) 元组 (matched block hashes, 非 request_id), 链式 hash 语义。
- `PendingLoadGroup`: owner 持全部 IO (acquire refs / reserve target / staging / AsyncLoadJob), waiter 持 0 (只 join `group.waiters`)。
- 单次 CPU→MLU promotion: owner load complete → commit L1 → waiter 下次 schedule 走正常 L1 lookup 共享 physical blocks。
- CPU refcount=1 (只 owner acquire, waiter 不 +1), 与 waiter 数量无关。
- owner 失败 → resolve group (waiter 回 waiting, 可恢复), refs/staging 全释放。

本阶段新增 `test_quantized_coalescing.py` (INT8 KV+Scale, 116 测试) 验证量化路径下全部正确。

## §6 P2 Adaptive Sync/Async Load Policy 实现回顾 (Step 9, 本阶段量化验证)

`_decide_load_policy` + `_has_other_ready_compute`:
- 同 prefix 已 pending → join waiter (coalesce, 不论 policy)。
- `always_sync` → sync; `always_async` → async。
- `adaptive`: 有其他 ready compute (running 非空 OR waiting 有其他可调度 seq) → async (overlap); 否则 → sync (无 overlap 收益, sync 省一次 round-trip)。

本阶段 `test_quantized_coalescing.py` §Q6/§Q7/§Q8 验证: 单请求 adaptive 选 sync, 有 compute 选 async, 同 prefix coalescing 后 load_count=1 (无论 policy)。

## §13 §B5 P0 Stream Dependency 开销

| scenario | value |
|----------|-------|
| in-flight async D2H latency (256 block, 4096 token) | 9.23ms |
| device_sync host block (有 in-flight D2H) | 9.09ms |
| producer_event pure record+wait (非阻塞) | 52.04us |
| P0 收益 (device_sync / producer_event) | **175x** |

**关键收益**: 原热路径 `torch.mlu.synchronize()` 是 device-wide barrier, 在有 in-flight async D2H (前一个请求的 Store, ~9ms) 时, host 阻塞 ~9ms 等其完成。P0 的 `producer_event.record()` + `wait_event` 是非阻塞 host API (只建流依赖), 每请求新增仅 ~52us。**热路径 host 阻塞从 ms 级降至 us 级, 改善 175x**。这是移除热路径 device sync 的核心收益 (在有并发 async Store 的真实多请求场景下显著)。

## §24 16 个最终问题

**Q1: P0 的 producer_event 在哪个 stream record? 为什么?**
default/compute stream (model forward 写 KV 的流)。保证 record 在最后一次 KV/Scale 写之后, wait_event 让 pack 等该写完成。

**Q2: pack_stream.wait_event 与 transfer_stream.wait_event 的区别?**
wait_event 必须在执行 pack 的 stream 上。Async Store 分流: pack 在 pack_stream → wait_event 在 pack_stream; sync store (pack+D2H 同 transfer_stream) → wait_event 在 transfer_stream。

**Q3: 为什么移除热路径 torch.mlu.synchronize() 是安全的?**
producer_event + wait_event 建立精确跨流依赖 (pack 只等 forward 写); load 的 transfer_stream.synchronize (stream-local) 足够供 default 读 target (实证 INT8 0/300)。device-wide sync 冗余且引入 ms 级 host 阻塞 (§13)。

**Q4: 移除后 store source 生命周期是否仍精确?**
是。pack_stream.synchronize 保证 pack 完成 (source 已读进 staging), D2H 只依赖 staging。submit 返回 → deallocate 安全。实证: 覆盖 source 后 D2H bit-exact (test_stream_dependency §8)。

**Q5: async load consumer 可见性如何保证?**
Event record 在 unpack 之后 (transfer_stream)。poll query=True → commit → seq 回 waiting → 下 step default prefill。transfer_stream 写早已完成 (Event complete 蕴含) + submit 时 synchronize 已建立顺序。实证 INT8 0/300。
**Q6: PendingPrefixKey 为什么用 matched block hashes 而非 request_id?**
同 prefix 的不同请求应合并到同一 group (共享一次 H2D)。request_id 每请求唯一, 无法合并。matched block hashes (l1_hit, l2_hit, last_hash) 标识 prefix 语义, 同 prefix 请求 key 相同 → 合并。

**Q7: owner 与 waiter 的 IO 持有区别?**
owner: acquire CPU refs / reserve target MLU blocks / acquire staging / submit AsyncLoadJob (持全部 IO)。waiter: 只 join group.waiters (持 0 IO, 无 H2D, 无 staging, 无 ref)。

**Q8: CPU refcount 为何与 waiter 数量无关?**
只 owner acquire refs (refcount=1)。waiter 不 acquire (不重复保护 source CPU block)。owner load complete → release refs (refcount=0)。waiter 通过 L1 lookup 共享已 promote 的 MLU physical blocks, 不读 CPU。

**Q9: group 完成后 waiter 如何共享 MLU blocks?**
owner commit → hash→block_id 注册 L1 → owner 回 waiting。waiter 回 waiting → 下次 schedule 走正常 L1 lookup, allocate_prefix 命中已注册 hash, 复用同一组 MLU physical blocks (ref_count 反映共享)。

**Q10: owner 失败如何恢复 waiter?**
_fail_pending_load: rollback target MLU blocks (回 free_list), release CPU refs, release staging, 删除 group, owner+waiter 全回 waiting。waiter 下次 schedule 重新走 L1→L2→ (重新 load 或 coalesce), 不丢失。

**Q11: adaptive 何时选 sync? 何时 async?**
sync: 单请求 (无其他 ready compute, 无 overlap 收益, sync 省一次 round-trip)。async: 有其他 ready compute (running 非空 OR waiting 有其他可调度 seq), load 与 compute 重叠。同 prefix 已 pending → join waiter (不论 policy)。

**Q12: coalescing 如何消除同 prefix 吞吐退化?**
同 prefix 并发, 首个 owner 发起唯一一次 H2D, 后续 join waiter (无重复 H2D)。owner promote 后 waiter 共享 physical blocks。load_count=1 (§B1), HoL spread=0 (§B2)。

**Q13: 2/4/8 same-prefix load_count 为何都是 1?**
coalescing: 同 prefix_key 只 1 group, 1 owner, 1 AsyncLoadJob。waiter 不发起 H2D。故无论 nreq, load_count=1 (§B1)。

**Q14: 5000-op 压力如何保证无泄漏/无死锁?**
每 100 op 抽查 invariant (free+ready+pending=capacity, ref≥0, staging 一致), 终态全 0 (pending_store/load/protected)。groups_peak=1 (无 group 堆积)。全部 is_finished (无死锁)。
**Q15: device_wide_sync_hotpath_count 为何恒 0?**
P0 移除全部 5 处热路径 torch.mlu.synchronize(), 改用 producer_event + stream-local sync。metrics 计数器在热路径 sync 处递增 (已移除, 故恒 0)。全测试验证。

**Q16: P0 在有并发 async Store 时的收益量化?**
原 device_sync host 阻塞 ~9ms (等 in-flight D2H); P0 producer_event 非阻塞 ~52us。改善 175x (§B5)。多请求并发场景下, 每请求 store 不再阻塞 host 等前一个 D2H, store 可与 compute/D2H 重叠。

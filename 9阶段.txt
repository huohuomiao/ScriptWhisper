# 1. 当前 INT8 KV Cache 实现

通过 monkey-patch (`optimization_kvcache/kvcache_patch.py`) 注入, 原版 `attention.py` / `attention_mlu.py` / `model_runner.py` 一行不改。三个注入点:

1. **`Attention.forward`** → `_patched_attention_forward`: 把 `k_scale/v_scale` 传给量化版 ops
2. **`ModelRunner.allocate_kv_cache`** → `_patched_allocate_kv_cache`: 分配 int8 cache + fp32 scale, 挂到各层
3. **store/decode/prefill attention** 用本模块量化版函数 (通过 forward 调用)

| 路径 | 写入 | 读取 |
|------|------|------|
| store_kvcache | `quant_to_paged_cache` (bf16→int8+scale, 算子内部自动算 per-token scale) | — |
| Decode | — | `single_query_cached_kv_attn(..., k_scale, v_scale, kv_cache_quant_bit_size=8)` 算子内部反量化 |
| 普通 Prefill (block_tables=None) | 新算 bf16 K/V 直接走 `flash_attention` (不读 cache) | — |
| Prefix HIT Prefill (block_tables≠None) | — | 只 gather 实际引用的 int8 blocks → MLU 反量化成 compact bf16 → remap block_tables → `flash_attention` |
| CUDA fallback | `reshape_paged_cache` (bf16 直写) | `single_query_cached_kv_attn` (不传 scale) |

**关键约束**: `flash_attention` 不支持读 int8 cache (要求 q/k dtype 一致, 见 `test_flash_int8.py` 的 `CNNL_STATUS_BAD_PARAM`), 故 prefix-cache prefill 必须先反量化成 bf16。

# 2. KV / Scale Layout

| 张量 | shape | dtype | 说明 |
|------|-------|-------|------|
| kv_cache | `(2, L, num_blocks, H, T, D)` = `(2, 36, B, 8, 16, 128)` | int8 | MLU layout: head 维在 block_size 前 |
| kv_scales | `(2, L, num_blocks, H, T)` = `(2, 36, B, 8, 16)` | float32 | per-token-per-KV-head scale |
| 单层 k_cache | `(num_blocks, 8, 16, 128)` | int8 | `module.k_cache = kv_cache[0, layer_id]` |
| 单层 k_scale | `(num_blocks, 8, 16)` | float32 | `module.k_scale = kv_scales[0, layer_id]` |

量化粒度: **per-token-per-KV-head** (scale shape 最后一维是 block_size=T, 即每个 token 一个 scale)。

# 3. 容量预算修正

**修正前 (问题 A)**: `block_bytes = 2*L*H*T*D*1` (只按 int8 本体 itemsize=1), 漏掉 FP32 scale → "容量严格 2.00x" 不严谨。

**修正后** (`_patched_allocate_kv_cache`):
```python
int8_kv_bytes = 2 * L * T * H * D * 1        # int8 本体
scale_bytes   = 2 * L * T * H * 4            # FP32 per-token scale
block_bytes   = int8_kv_bytes + scale_bytes  # scale 纳入预算
```

| 分量 | bytes | MiB |
|------|-------|-----|
| bf16_block_bytes | 2×36×8×16×128×2 = 2,359,296 | 2.2500 |
| int8_kv_bytes | 2×36×8×16×128×1 = 1,179,648 | 1.1250 |
| scale_bytes (fp32) | 2×36×8×16×4 = 36,864 | 0.0352 |
| **int8_total_block_bytes** | **1,216,512** | **1.1602** |
| scale_overhead_ratio | 3.03% | |
| **capacity_ratio** = bf16/int8_total | **1.9394x** | (非 2.00x) |

# 4. 理论容量倍率

**1.9394x** (非 2.00x)。FP32 scale 占每 block 3.03%, 吃掉部分容量收益。

# 5. 真实容量倍率

固定 KV budget (gpu_memory_utilization=0.9) 实测 (`test_budget.py` / `benchmark_capacity.py`, 真实模型加载):

| mode | num_blocks | capacity_tokens | block_bytes | kv_payload_MB | scale_MB | total_kv_MB | model_fixed_GB | HBM_used_GB | peak_alloc_GB |
|------|-----------|----------------|-------------|--------------|----------|-------------|----------------|-------------|---------------|
| bf16 | 20,603 | 329,648 | 2,359,296 | 46,165 | 0 | 46,165 | 21.70 | 66.78 | 66.45 |
| int8 | 39,958 | 639,328 | 1,216,512 | 44,767 | 1,399 | 46,166 | 21.70 | 66.78 | 66.45 |

- **actual_capacity_ratio = 639,328 / 329,648 = 1.9394x**
- 与理论 1.9394x **完全一致** (误差 < 0.01%)
- 两种模式 total KV 显存几乎相同 (~46GB), int8 用同样显存装下 1.94x 的 block
- model_fixed (权重+其它) 两种模式相同 (21.70GB), 证明差异只来自 KV budget

**若仍为 2.00x**: 说明 scale 未纳入预算 (修正前的 bug)。修正后实测 = 1.94x, 与理论一致。

# 6. Prefix Block Map stale cache 风险

**修正前 (问题 B)**: 模块级全局 dict `_prefill_block_map_cache`, key = `(data_ptr, shape)`。
- 风险: block_tables 张量 data_ptr 不变、shape 不变, 但内容被原地改写 → 旧 key 仍命中 → 返回基于旧内容的 mapping (stale)。
- `test_block_map_cache.py` 复现: `[1,2,3,4]` 计算后原地改 `[1,2,3,9]`, data_ptr/shape 不变 → 旧实现返回 `[1,2,3,4]` (stale)。

**确认 stale bug 存在** (修正前)。

# 7. Context-Level Mapping Cache 修正

**修正后** (`_compute_block_map`):
1. 映射结果挂到 `context.kv_quant_block_map` (新增字段, 见 `nanovllm/utils/context.py`)
2. `set_context()` 每次 forward 创建新 `Context` → `kv_quant_block_map=None`, 天然按 forward 失效
3. 同一 forward 内 36 层 × 2(k/v) = 72 次调用复用同一映射, 只算一次
4. **内容指纹校验**: key = `(data_ptr, shape, (首元素, 末元素, 非负元素数))`。data_ptr/shape 不变但内容变时, 采样点变化 → 失效重算, 修复 stale bug
5. 计数器 `block_map_compute_count` 验证 "每 forward 只算一次"

**验证结果** (`test_block_map_cache.py` 18/18 PASS):
- 72 次调用只计算 1 次 ✓
- 新 forward 重新计算 ✓
- data_ptr 不变内容改变 → 重算 (无 stale) ✓
- batch size 改变 → 重算 ✓
- prefix length 改变 → 重算 ✓
- -1 padding 正确处理 ✓
- 随机离散 physical blocks 重映射到 [0,1,2,3] ✓

**真机验证** (prefix-hit prefill): `block_map_compute_count` 在一次 prefix-hit prefill 前后 delta = **1** (每 forward 1 次, 不是 72 次)。

# 8. Store Quantization

`_patched_store_kvcache` → `ops.quant_to_paged_cache(k, v, k_cache, v_cache, k_scale, v_scale, slot_mapping)`:
- 算子内部自动算 per-token scale = max(|k|)/127, 存 int8 + scale
- 动态量化 (每写一个 token 量化一次), 无需离线校准
- int8 range 实测 [-127, 127] ✓, scale finite & nonzero ✓ (`test_correctness.py`)

# 9. Decode INT8 Attention

`_patched_decode_attention` → `ops.single_query_cached_kv_attn(..., k_scale, v_scale, kv_cache_quant_bit_size=8)`:
- **算子内部反量化**, 直接读 int8 cache, 无 host dequant
- `test_kv_paths.py` 确认: decode 路径 KV 大数据不经过 CPU
- 无 NaN/Inf, rel_err < 5% (见 §12)

# 10. Cold Prefill

- int8 相对 bf16 的 prefill 开销: **0.4% ~ 6.9%** (quant store 成本, `quant_to_paged_cache` 比 `reshape_paged_cache` 稍贵)

# 11. Prefix HIT Dequant Path

`_patched_prefill_attention` (block_tables≠None, int8 路径):
```
block_tables → _compute_block_map (CPU unique+searchsorted, 每 forward 1 次)
→ _dequant_used_blocks: index_select(used) + mul(scale) + cast(bf16)  [全在 MLU]
→ compact bf16 KV + remapped block_tables
→ flash_attention
```

**KV 大数据不经过 CPU** (`test_kv_paths.py`): 只 block_tables (int32, KB 级) / used ids / remapped bt 经过 CPU; int8 KV / scale / compact bf16 全在 MLU。`compact.device.type == "mlu"` ✓。

**只反量化 used blocks** (`test_kv_paths.py`): compact_blocks == unique used blocks (4 == 4), 未反量化整个 cache (1000 blocks 只反量化 4)。dequant_bytes = 0.25MB (全 cache 反量化会 62.5MB)。

**Block Remap Correctness** (`test_kv_paths.py`): 随机离散 physical blocks [7,21,35,80], 原 bf16+原bt vs INT8→compact+remapped_bt, attention 输出 max_abs_err=0.000366, rel_err=3.62% < 5% ✓。

**Block Map CPU 开销** (`test_kv_paths.py`): 1~512 blocks, 各阶段 170~181µs (copy 40µs + unique 30µs + search 10µs + upload 96µs)。context cache 后每 forward 只算 1 次, 开销可忽略。

# 19. 当前瓶颈

1. **Prefix HIT dequant 开销**: ~15ms / prefill (72 次 index_select+mul+cast), 导致 int8 prefix-hit TTFT 比 bf16 慢 1.39~1.65x。根因: `flash_attention` 不支持读 int8 cache, 必须反量化成 bf16。这是 **int8 KV 的主要性能代价**, 集中在 prefix-hit 路径。
2. **compact BF16 临时显存**: 随 prefix 线性增长 (8192 → 1.15GB), 虽当前无 OOM, 但超长 prefix (16K+) 需关注。
3. **Decode 收益小**: int8 对 TPOT 中性 (0.97~1.05x), 因 decode attention 仅占 ~5% TPOT, 不在主瓶颈。
4. **容量收益是主要价值**: 1.94x 容量 → 1.94x 并发 / 更长上下文, 而非降延迟。

# 20. 是否建议与 CPU L2 Offload 合并

**建议: 具备进入 Quantized Hierarchical Prefix KV Cache 的条件, 但下一阶段必须专门约束/优化 Prefix HIT。**

理由:
- ✅ 容量预算修正完成 (scale 纳入, 1.94x 真实)
- ✅ block-map stale 风险修复 (context 级 + 内容指纹)
- ✅ 每 forward block map 只算 1 次
- ✅ KV 大数据不经过 CPU
- ✅ 三条路径 correctness 通过 (decode / cold prefill / prefix HIT)
- ✅ random physical blocks remap 通过
- ✅ 容量 1.94x, 并发 1.94x
- ✅ decode 性能中性, peak memory 无 OOM 风险
- ⚠️ Prefix HIT dequant 开销 ~15ms, TTFT 慢 1.39~1.65x (可接受但有优化空间)
⚠️ Prefix HIT dequant 开销 ~15ms, TTFT 慢 1.39~1.65x (可接受但有优化空间)
- ⚠️ compact BF16 临时显存随 prefix 增长 (8192=1.15GB, 当前安全)

**下一阶段接口分析 (只分析, 不实施)**: 若 CPU L2 存 INT8+scale:
- 4096 BF16 KV ≈ 576MB; INT8+FP32 scale ≈ 576/1.94 ≈ 297MB
- CPU→MLU H2D 数据量理论接近减半 (1.94x)
- 但 CPU L2 当前存的是 BF16 (kv_offload 主流程), 改成 INT8 需 CPU 端反量化或 MLU 端 pack, 复杂度上升
- 本阶段不修改 CPU L2 Offload 主流程

# 最终必须回答的 14 个问题

1. **INT8 block_bytes 是否已经计入 scale?**
   是。修正后 `block_bytes = int8_kv_bytes + scale_bytes = 1,216,512` (含 FP32 scale)。

2. **BF16 block / INT8 KV / scale 分别多少 bytes?**
   - BF16 block = 2,359,296 bytes (2.25 MiB)
   - INT8 KV = 1,179,648 bytes (1.125 MiB)
   - scale (fp32) = 36,864 bytes (0.0352 MiB)

3. **真实有效容量倍率是多少? 是否仍为 2.00x?**
   **1.9394x, 不再是 2.00x**。实测 639,328/329,648 = 1.9394, 与理论完全一致。

4. **FP32 scale 占每 block 比例多少?**
   **3.03%** (36,864 / 1,216,512)。

5. **FP16/BF16 scale 是否支持?**
   **不支持**。`single_query_cached_kv_attn` 要求 `key_cache_quant_scale_desc_dtype == CNNL_DTYPE_FLOAT`, fp16/bf16 报 `CNNL_STATUS_BAD_PARAM`。正式 baseline 保持 FP32 scale。

6. **data_ptr+shape map cache 是否存在 stale bug?**
   修正前存在 (data_ptr/shape 不变内容变 → 返回旧 mapping)。**已修复**: 改用 context 级缓存 + 内容指纹 (首/末元素 + 非负数), 内容变化即失效重算。

7. **Context-level cache 是否每 forward 只计算一次?**
   是。`set_context()` 每次 forward 创建新 Context → `kv_quant_block_map=None` 自动失效; 同 forward 72 次调用复用, 真机实测 delta=1。

8. **Decode 是否真正直接读 int8 cache、无 host dequant?**
   是。`single_query_cached_kv_attn` 算子内部反量化, KV 不离开 MLU。`test_kv_paths.py` 确认 compact/used_ids/new_bt 均在 MLU。

9. **Cold Prefill 的 quant store overhead 是多少?**
   **0.4% ~ 6.9%** (512: -0.4%, 1024: 6.4%, 2048: 6.9%, 4096: 6.2%, 8192: 5.5%)。此路径无历史 KV dequant。

10. **Prefix HIT 的 dequant latency / compact BF16 临时显存是多少?**
    - dequant latency: **~15-16ms** (稳定, 72 次 index_select+mul+cast)
    - compact BF16 临时显存: 72MB(512) → 1152MB(8192), 8192 时 1.15GB, peak 66.53GB (无 OOM)

11. **512~8192 context 下 Decode TPOT 相比 BF16 如何?**
    基本持平 (speedup 0.97~1.05x)。短 ctx/小 batch 略慢 (0.97x), 长 ctx/大 batch 略快 (1.05x)。8192: 54.24→55.69ms (0.97x)。int8 对 decode 延迟中性。

12. **token match / attention error 如何?**
    - attention relative error: avg 3.47%, max 3.83% (单算子)
    - token match rate (近 greedy temp=0.01): 86.9% (5 prompt 平均)
    - 无 NaN/Inf

13. **INT8 Prefix HIT 是否存在明显 peak-memory/OOM 风险?**
    **当前无明显风险**。8192 prefix compact BF16 = 1.15GB, peak 66.53GB (80GB 卡余量充足)。但 compact 随 prefix 线性增长, 超长 prefix (16K+) 需关注。

14. **是否具备进入 Quantized Hierarchical Prefix KV Cache 的条件?**
    **具备**。容量预算修正、block-map 生命周期、三条路径 correctness、容量 1.94x、peak memory 安全均已验证。Prefix HIT dequant 开销 (~15ms) 是已知限制, 下一阶段需专门优化 (如 flash_attention 支持 int8, 或流式 dequant)。

 最终裁决

## **B. PASS WITH LIMITATION**

**理由**:
- Decode 和容量收益良好 (TPOT 中性 0.97~1.05x, 容量 1.94x, 并发 1.94x)
- 三条路径 correctness 全通过, 无 NaN/Inf, attention error ~3.5%
- 容量预算修正完成, block-map stale 修复, 每 forward 只算 1 次, KV 不经过 CPU

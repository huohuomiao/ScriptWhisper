## 一、KV Cache 结构确认

以源码为准（与上一阶段 probe 一致，未改动任何源码）：

| 参数 | 值 | 来源 |
|---|---|---|
| 模型 | Qwen3-8B | — |
| **KV shape (MLU)** | `(2, 36, num_blocks, 8, 16, 128)` | `platform.py:kv_cache_shape()` MLU 分支 |
| **dtype** | bfloat16 (itemsize=2) | `hf_config.dtype` |
| num_layers | 36 | `num_hidden_layers` |
| num_kv_heads | 8 | `num_key_value_heads` (TP=1) |
| head_dim | 128 | `hidden_size/num_attention_heads` |
| block_size | 16 | `config.py` (MLU 默认) |
| **单个逻辑 block 大小** | **2.25 MB** | `2×36×8×16×128×2 = 2,359,296 bytes` |

**维度顺序**（MLU）：`(K/V, layer, block, kv_head, token_in_block, head_dim)`。

`model_runner.py:allocate_kv_cache()` 确认：`module.k_cache = self.kv_cache[0, layer_id]`，`module.v_cache = self.kv_cache[1, layer_id]` —— 即 **layer = index 1，block = index 2**。物理 block id 直接对应 tensor 的第 2 维索引：`kv[:, :, block_id, :, :, :]`。

**连续性**（关键，决定性能）：
- `kv[:, :, block_id, ...]`（跨层单 block）→ `is_contiguous() = False`，是 36 个分散的 32KB 小块（每层一个），物理内存按 layer 外层、block 内层排列。
- `kv[k, layer, :, ...]`（单层所有 block）→ **连续**。
- `kv[:, :, 0:N, ...]`（跨层 N 个连续 block）→ strided（block 维在 layer 维之内），`is_contiguous() = False`。

CPUKVPool 采用与 MLU **完全一致**的 layout `(2, 36, cpu_num_blocks, 8, 16, 128)`，便于 store/load 时直接对应、bit-exact。

## 二、CPUKVPool 设计

`cpu_kv_pool.py` 实现 CPU pinned memory 中的 KV block 池，职责：预分配 buffer、分配/释放 block id、返回 block view。

**核心设计**：
- `self.kv = torch.empty((2, num_layers, num_blocks, num_kv_heads, block_size, head_dim), dtype=bfloat16, device="cpu", pin_memory=True)`，构造时校验 `is_pinned()==True`（否则抛 RuntimeError，因为 pinned 是 H2D/D2H 带宽的前提）。
- 默认 `num_blocks=128`，总占用 `128 × 2.25MB ≈ 288MB`（与 spec 一致）。
- **free-list 分配器**：`_free` 为**有序列表**（升序），`_used` 为 set。
  - `allocate(n)`：`pop(0)` 取最小的 n 个 id → **返回升序连续 id**（关键：使 store/load 的 contig 快路径生效，可用 slice 表达）。
  - `free(ids)`：`bisect.insort` 插回 `_free` 保持升序 → 重复 alloc/free 仍能分到连续 id。
  - 超容量申请 → RuntimeError（不 silent truncation）。
  - double free / 非法 id → RuntimeError（不 silent corruption）。
- `get_block(id)` 返回 strided view `kv[:, :, id, ...]`（与 MLU block 同形同 stride，`is_contiguous()==False`）。
- `get_blocks(ids)`：连续 id 返回 strided slice（view）；离散 id 返回 advanced-index materialize（新 contiguous tensor，非 view）。
- 查询接口：`capacity` / `num_free_blocks()` / `num_used_blocks()` / `is_pinned()`。
**为何升序分配**：prefix cache 的 block 通常部分连续，升序分配使 `cpu_block_ids` 多为连续 run，命中 store/load 的 slice 快路径。这是纯 allocator 层的优化，不影响对外语义。

## 三、CPU Memory Layout

与 MLU KV Cache **完全一致**：`(2, 36, cpu_num_blocks, 8, 16, 128)` bf16，`pin_memory=True`。

- 单 CPU block = `kv[:, :, block_id, :, :, :]`，shape `(2, 36, 8, 16, 128)`，2.25MB，strided（跨层），与 MLU physical block **同形同 stride**。
- 这保证 store/load 时 strided slice 可直接 `copy_` 对应，无需 pack/unpack（上一阶段 probe 结论 A 的前提）。
- 物理内存同样按 layer 外层、block 内层排列：`cpu_pool[k, layer, :, ...]` 单层连续，`cpu_pool[:, :, block_id, ...]` 跨层 strided。

**实测带宽特性**（本阶段系统诊断，见第五节）：CPU 端访问 block-dim-in-middle 的池，无论读或写、连续 slice 或离散 advanced-index，大规模下都只有 **~0.7–1.2 GB/s**（host 端 strided 访问固有特性）。这是该 layout 在 host 端的性能约束，DMA 段（D2H/H2D）本身不受其影响。

## 四、Store 路径（MLU → CPU，D2H）

`KVBlockMover.store(mlu_block_ids, cpu_block_ids)`：按位置一一对应 `CPU[cpu_block_ids[i]] <- MLU[mlu_block_ids[i]]`。

**架构（单次 copy，无 per-layer host 循环）**：

```
step 1+2 (transfer_stream):  MLU blocks -> contig pinned CPU staging (D2H)
step 3 (host):               contig CPU staging -> CPU 池 (单次 copy)
```

- **source 连续 (run，升/降序)**：`cpu_staging.copy_(mlu_kv[:, :, slice, ...], non_blocking=True)` —— D2H 引擎能高效处理 strided MLU source，单次 copy ~31 GB/s（实测），无需 gather。
- **source 离散**：先 on-device gather `staging_m.copy_(mlu_kv[:, :, idx_s, ...])`（设备内，快），再 D2H `cpu_staging.copy_(staging_m, non_blocking=True)`（contig→contig，~31 GB/s）。
- **D2H 后必须 `transfer_stream.synchronize()`**：`non_blocking` D2H 异步，step 3 在 host 读 `cpu_staging`，必须等 D2H 完成否则读到旧数据（这是本阶段调试中修复的关键 race）。
**host 写池 (step 3)**：
  - dst 连续 (run)：`cpu_pool.kv[:, :, slice, ...].copy_(cpu_staging)` —— 单次 slice copy。
  - dst 离散：`cpu_pool.kv[:, :, idx_d, ...] = cpu_staging` —— 单次 advanced-index 写（~0.7–0.9 GB/s，host 端离散写池固有瓶颈）。

**staging buffer 复用**：`_get_cpu_staging(n)` / `_get_mlu_staging(n)` 按需扩展、跨调用复用，**不在循环里 malloc**（spec 要求）。

---

## 五、Load 路径（CPU → MLU，H2D）

`KVBlockMover.load(cpu_block_ids, mlu_block_ids, method="index_copy_")`：按位置一一对应 `MLU[mlu_block_ids[i]] <- CPU[cpu_block_ids[i]]`。

**架构（单次 copy，无 per-layer host 循环）**：

```
step 1 (host):               CPU 池 -> contig pinned CPU staging (单次 copy)
step 2+3 (transfer_stream):  contig CPU staging -> contig MLU staging (H2D) -> on-device scatter
```

- **host 读池 (step 1)**：
  - source 连续 (run)：`cpu_staging.copy_(cpu_pool.kv[:, :, slice, ...])` —— 单次 slice copy。
  - source 离散：`cpu_staging.copy_(cpu_pool.kv[:, :, idx_s, ...])` —— 单次 advanced-index gather（~0.7–1.2 GB/s，host 端离散读池固有瓶颈）。
- **H2D (step 2)**：`staging_m.copy_(cpu_staging, non_blocking=True)` —— contig pinned → contig MLU，~22 GB/s（实测）。
- **on-device scatter (step 3)**，三种 method（benchmark 对比）：
  - `advanced`：`mlu_kv[:, :, idx_d, ...] = staging_m`（advanced-index 赋值，写真实 KV tensor）。
  - `index_copy_`（默认）：`mlu_kv.index_copy_(2, idx_d, staging_m)`（沿 block 维 dim=2）。
  - `contig_run`：把 `mlu_block_ids` 拆成升序连续段，每段 slice copy `mlu_kv[:, :, run, ...].copy_(staging_m[:, :, seg, ...])`。
  - dst 连续时，所有 method 统一走 slice copy（最快，无 scatter 算子开销）。
- 末尾 `transfer_stream.synchronize()` 保证返回时数据已 ready（同步对外接口）。

**advanced-index 陷阱（spec 强调）**：`mlu_kv[:, :, idx, ...]`（读）会 materialize 临时 tensor，但 `mlu_kv[:, :, idx, ...] = src`（写）是写真实 KV tensor。正确性测试直接从原始 `mlu_kv` 读取 `restored = mlu_kv[:, :, dst_idx, ...].clone()` 验证，确认真实 tensor 被修改（见第七、八节）。

## 六、Physical Block Remapping

核心验证目标：源 MLU block id 与目标 MLU block id 可**完全不同**，经 CPU 中转后 bit-exact 恢复。

**测试流程**（`test_store_load.py`，每组 mapping）：
1. `init_region(mlu_kv, src_ids)`：把 src 区段重置为确定性数据（整 block = block_id 值）。
2. `torch.mlu.synchronize()`（init 在 default stream，store 在 transfer_stream，跨流同步）。
3. `orig = read_blocks(mlu_kv, src_ids)`：保存源副本（直接从原始 tensor clone）。
4. `mover.store(src_ids, cpu_ids)`：MLU src → CPU。
5. `mlu_kv[:, :, dst_idx, ...] = 0` + `torch.mlu.synchronize()`：清零目标（default stream 写，load 在 transfer_stream 写同批 dst，跨流同步防 zero 在 load 后执行）。
6. `mover.load(cpu_ids, dst_ids, method)`：CPU → MLU dst。
7. `torch.mlu.synchronize()`（load 在 transfer_stream 写，restored 在 default stream 读，跨流同步）。
8. `restored = read_blocks(mlu_kv, dst_ids)`：直接从原始 tensor 读取目标。
9. `torch.equal(restored, orig)`：bit-exact 校验。

**关键跨流同步点**（本阶段调试修复的 race）：
- init(default) → store(transfer)：防 store 读到 init 前旧数据。
- zero(default) → load(transfer)：防 zero 在 load 后执行覆盖结果。
- load(transfer) → restored(default)：防 restored 读到 load 前旧数据。
- store 内 D2H(non_blocking) → host scatter：防 host 读到 staging 旧数据。

**remapping 示例**（spec 要求的 MLU[7,21,35,80] → CPU[0,1,2,3] → MLU[101,18,53,66]）：测试用 `src_ids`（base=10 区段，连续或 step=37 散布）与 `dst_ids`（base=600 区段，与 src 完全不相交），经 CPU pool 中转后 `restored[i] == orig[i]`（按位置一一对应），即 dst_ids[i] 现在的内容 == 原 src_ids[i] 的内容。108 项全部 bit-exact。

- **host 读池段（CPU 池 → contig CPU staging）：~0.7–1.2 GB/s**（大规模）—— **这是 load 的瓶颈**。

- H2D 段（contig CPU staging → contig MLU）：**~18.6–22.7 GB/s**（快）。

**关键不对称**：D2H 能高效处理 strided MLU source（~31 GB/s），但 **H2D 不能高效读 strided CPU source**（~1 GB/s）。因此 load 的离散 src 无法像 store 那样靠"on-device gather"规避——必须先在 host 端 gather 到 contig（慢），再 contig H2D。这是 D2H/H2D 引擎的能力差异，非实现问题。

## 十一、Random Load 三种方法对比

对 random→random，比较 advanced / index_copy_ / contig_run（`sync_load_methods.csv`）：

| blocks | advanced GBps | index_copy_ GBps | contig_run GBps |
|---|---|---|---|
| 16 | 1.12 | 1.38 | 1.43 |
| 64 | 1.38 | 1.38 | 1.40 |
| 128 | 0.70 | 0.70 | 0.71 |
| 256 | 1.44 | 1.84 | 1.61 |

**结论**：
- 三种 method 带宽**接近**（差异 < 2x），因为它们共享同一个 host 读池瓶颈（step 1），on-device scatter 段（step 3）的差异被 host 瓶颈淹没。
- `index_copy_` 在大规模（256）略优（1.84 vs advanced 1.44 vs contig_run 1.61），小规模三者相当。
- `contig_run` 在 dst 有连续段时理论最优（减少 scatter 次数），但本测试 dst 全离散（每段长 1），优势不显现；对真实 prefix cache（dst 部分连续）会更好。
- **默认 method 用 `index_copy_`**：稳定、大规模最优、语义清晰（沿 block 维替换）。

## 十二、当前瓶颈

**唯一瓶颈：host 端访问 block-dim-in-middle 的 CPU 池（读或写），大规模下 ~0.7–1.2 GB/s。**

根因：CPU 池 layout `(2, 36, N, 8, 16, 128)` 的 block 维（index 2）在 layer 维（index 1）之内。访问 `pool[:, :, block_ids, ...]`（跨层）是 strided，物理上是 36 个分散小块的访问，host 端单次 `copy_` 对此 strided 访问只能 ~0.7–1.2 GB/s（无论读/写、slice/advanced-index）。

**不是瓶颈的部分**（实测确认）：
- D2H（strided MLU → contig CPU）：~31 GB/s（D2H 引擎能处理 strided source）。
- H2D（contig CPU → contig MLU）：~22 GB/s。
- on-device gather（离散 MLU → contig MLU）：快。
- on-device scatter（contig MLU → 离散 MLU）：102–385 GB/s（极快）。
**为何 per-layer 拆 72 次小 copy 不行**：曾尝试把 host 端访问拆成 per-layer（单层连续 `pool[k, layer, ...]`），用 Event 计时显示 ~31 GB/s，但那是**只测了 transfer_stream 的 GPU 时间**，隐藏了 host 端 72 次 dispatch 的 wall-clock 开销。实测 wall-clock per-layer 反而 ~600ms（更慢），因为 72 次同步 host copy 各付固定开销。**最终采用单次 copy（slice 或 advanced-index），wall-clock 最优。**

**缓解方向（本阶段不实施，供下一步参考）**：
1. **保持 block_ids 连续**（prefix cache 的 block 通常部分连续）：连续 run 走 slice 快路径，且真实场景下 host 端访问的是连续大段而非全离散。
2. **改 CPU 池 layout 为 layer-outer**（`pool[k, layer, :, ...]` 单层连续，按层 offload）：单层所有 block 连续，host 端访问 ~31 GB/s。但这偏离"与 MLU 完全一致 layout"的 spec，且 store/load 需 per-layer 调度。
3. **异步化**（下一步）：host 端 gather/scatter 与 compute 流水线重叠，隐藏 host 瓶颈（本阶段同步，无法重叠）。
4. **减少 offload 频率**：只 offload 长 prefix（大块连续），避免高频小离散 offload。

**与上一阶段 probe 的差异说明**：probe 测的是 `strided MLU → contig CPU`（D2H，~31 GB/s）和 `contig CPU → strided MLU`（H2D，~22 GB/s），**两端总有一端是 contig standalone tensor**，未测"strided CPU 池 ↔ strided MLU"的完整 store/load。本阶段接入真实 CPU 池后，host 端池访问成为瓶颈，这是 probe 未覆盖的真实约束。probe 的"结论 A：可直接 offload 无需 pack"在**正确性**和**DMA 段带宽**上成立，但在**完整 store/load 的 host 端池访问**上需要补充：host 端 strided 池访问 ~0.7–1.2 GB/s 是固有成本。

## 十三、能否进入 Prefix Hash 阶段

**能进入，但需带着本阶段的性能认知。**

理由：
1. **正确性完全 PASS**：141 项测试全 PASS，physical block remapping 全部 bit-exact，三种 load method 全正确。CPUKVPool 分配器（升序、超容量/double-free/非法 id 拒绝）完备。同步 store/load 接口可用。
2. **架构已定**：CPUKVPool + KVBlockMover 的同步接口（store/load + synchronize）可直接作为 Prefix Hash 阶段的底层搬运原语。Prefix Hash 阶段只需在其上加"hash → block id 映射 + lookup + 淘汰策略"，不改动本层。
3. **性能瓶颈已定位且可缓解**：瓶颈是 host 端 strided 池访问（~0.7–1.2 GB/s），非 DMA、非 scatter、非正确性。缓解路径明确（保持 block 连续 / 异步流水线 / 按层 offload），且 prefix cache 的 block 天然部分连续，实际工作负载会好于全离散 benchmark。

**进入 Prefix Hash 阶段前建议确认**：
- 真实 prefix 的 block 连续性（决定 store/load 实际带宽落在 0.7 还是更高）。
- 是否需要异步化以隐藏 host 瓶颈（同步 PoC 下 host 瓶颈无法与 compute 重叠）。
- offload 触发阈值（只 offload 长 prefix，避免高频小 offload 放大 host 开销）。
## 十四、8 个问题的回答

### 1. CPUKVPool 的内存 layout 是什么？是否 pinned？

Layout `(2, 36, cpu_num_blocks, 8, 16, 128)` bf16，与 MLU KV Cache **完全一致**。`pin_memory=True`，构造时校验 `is_pinned()==True`（实测 True），否则抛 RuntimeError。默认 128 blocks ≈ 288MB。

### 2. Store 路径如何处理连续 source 与离散 source？

- 连续 source（run，升/降序）：直接 `cpu_staging.copy_(mlu_kv[:, :, slice, ...], non_blocking=True)`，D2H 引擎处理 strided src，~31 GB/s，无需 gather。
- 离散 source：先 on-device gather `staging_m.copy_(mlu_kv[:, :, idx_s, ...])`（设备内，快），再 D2H `cpu_staging.copy_(staging_m)`（contig→contig，~31 GB/s）。
- 两者 D2H 段都 ~31 GB/s；之后 host 写池（连续 dst slice / 离散 dst advanced-index）。

### 3. Load 路径三种方法分别是什么？benchmark 哪种最快？

- `advanced`：`mlu_kv[:, :, idx, ...] = staging`（advanced-index 赋值）。
- `index_copy_`：`mlu_kv.index_copy_(2, idx, staging)`（沿 block 维 dim=2，默认）。
- `contig_run`：拆 dst 成升序连续段，每段 slice copy。
- **最快**：大规模 `index_copy_` 略优（256 blocks 1.84 GB/s），小规模三者相当。三者共享 host 读池瓶颈，scatter 段差异被淹没。默认用 `index_copy_`。

### 4. Physical block remapping 是否 bit-exact？如何验证？

**是。** 流程：保存 src 副本 `orig` → store 到 CPU → 清零 dst → load 到 dst → 直接从原始 `mlu_kv` 读 `restored` → `torch.equal(restored, orig)`。关键：`restored` 直接读原始 tensor（非临时 view），确认真实 KV tensor 被修改；跨流同步防 race。108 项全 bit-exact，无 dtype 转换。
### 5. Store/Load 性能相比理论带宽如何？瓶颈在哪？

- Store 大规模 0.9–1.9 GB/s，Load 0.7–1.8 GB/s，**远低于 D2H 32.9 / H2D 23.6 理论**。
- **瓶颈：host 端访问 block-dim-in-middle 的 CPU 池（读/写 strided 位置），~0.7–1.2 GB/s**。DMA 段（D2H ~31 / H2D ~22 GB/s）和 on-device scatter（102–385 GB/s）都不是瓶颈。
- 根因：block 维在 layer 维之内，跨层访问是 36 个分散小块，host 端 strided 访问固有 ~0.7–1.2 GB/s。

### 6. 连续 block 与离散 block 性能差异？

**接近**（store 256：contig→contig 1.81 vs random→random 1.76 GB/s；load 类似）。因为瓶颈是 host 端池访问，连续 slice 与离散 advanced-index 在 host 端都是 strided 访问，带宽同量级（~0.7–1.2 GB/s）。离散略慢（advanced-index 比 slice 多一点索引开销），但差异小。DMA 段对连续/离散都 ~31 GB/s（离散靠 on-device gather 规避）。

### 7. 当前 layout 是否适合做 Prefix KV Offload？

**适合，但 host 端池访问是已知成本。**
- 正确性 PASS，DMA 段（22–31 GB/s）和 scatter 段（100+ GB/s）都高效。
- host 端池访问 ~0.7–1.2 GB/s 是该 layout 在 host 的固有约束，但：(a) prefix cache block 天然部分连续，实际好于全离散 benchmark；(b) 可异步化隐藏；(c) 可按层 offload 规避。
- 不需要 pack/unpack（probe 结论 A 在正确性和 DMA 带宽上成立）。

### 8. 下一步该做什么？

1. **Prefix Hash + Lookup**：在 CPUKVPool/KVBlockMover 之上加 token-prefix hash → CPU block id 映射 + 查找 + 命中/未命中处理（本层不动）。
2. **淘汰策略**：LRU/ARC 管理 CPU pool 的 free list（当前是简单 free-list，无淘汰）。
3. **异步化**：把 host 端 gather/scatter 与 compute 流水线重叠（submit_store/submit_load + job/pending），隐藏 host 瓶颈。
4. **接入真实 generation**：Scheduler/BlockManager 在 prefix 命中时调用 store/load（当前是独立 PoC，未接入）。
5. **真实负载验证**：用真实 prefix 的 block 连续性确认实际带宽，定 offload 触发阈值。
## 十五、最终结论

| 维度 | 结果 |
|---|---|
| **正确性** | ✅ 141 项全 PASS（CPUKVPool 33 + Store/Load 108），physical remapping bit-exact，三种 load method 全正确 |
| **CPUKVPool** | ✅ pinned memory、升序 free-list 分配、超容量/double-free/非法 id 拒绝、view 接口完备 |
| **Store/Load 架构** | ✅ 单次 copy、staging 复用（无循环 malloc）、跨流同步正确、同步对外接口 |
| **性能（DMA 段）** | ✅ D2H ~31 GB/s、H2D ~22 GB/s、scatter 102–385 GB/s，均达理论 90%+ |
| **性能（host 池访问）** | ⚠️ ~0.7–1.2 GB/s，host 端 strided 池访问固有瓶颈，大规模 store/load 0.7–1.9 GB/s |
| **约束遵守** | ✅ 未改 Scheduler/BlockManager/Attention/Prefill/Decode；未实现 Prefix Hash/LRU/async/C++；未改 KV layout；未接入 generation |

### 结论：**B. PARTIAL PASS**

**理由**：
- **正确性维度 PASS**：physical block remapping 全部 bit-exact，CPUKVPool 功能完备，同步 store/load 接口正确可用，三种 load method 全验证。这是本阶段的核心目标，完全达成。
- **性能维度 PARTIAL**：DMA 段（D2H/H2D）和 on-device scatter 都达理论 90%+，但完整 store/load 受 host 端 strided 池访问瓶颈约束，大规模仅 0.7–1.9 GB/s，**未达"contiguous 路径 ≥90% 基线"的目标**（contig→contig 256 blocks store 1.81 GB/s vs D2H 32.9 GB/s 基线，仅 5.5%）。
- **瓶颈已定位且为 layout 固有**：非实现缺陷，是 block-dim-in-middle layout 在 host 端的固有成本（probe 未覆盖的真实约束）。缓解路径明确（保持 block 连续 / 异步化 / 按层 offload），且 prefix cache 实际负载会好于全离散 benchmark。

**为何不是 A（PASS）**：性能未达 ≥90% 基线目标，host 端瓶颈使大规模 store/load 带宽远低于理论。
**为何不是 C（FAIL）**：正确性完全达成，架构正确可用，DMA/scatter 段高效，瓶颈已定位且可缓解，可直接作为 Prefix Hash 阶段的底层原语。

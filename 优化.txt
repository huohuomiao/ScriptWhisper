# 优化报告：RMSNorm 融合（优化1）+ Full Graph 入图（优化2）+ W8A16 权重量化（优化3）

> **项目**：Nano-VLLM MLU 适配优化
> **环境**：单卡 MLU590-M9DG 80GB / torch_mlu 1.31.1 / torch_mlu_ops 1.10.1 / Qwen3-8B bf16
> **日期**：2026-08-20
> **优化类型**：优化1 算子融合（纯 API 替换）；优化2 Runtime 修改（Graph capture 范围扩展）；优化3 权重量化（bf16→int8 + 算子替换）
> **结论**：
> - **优化1（RMSNorm → fused_rms_norm）**：✅ 达成预期，TPOT -13.4%，吞吐 +20%，正确性无损，**采纳**
> - **优化2（Full Graph，LM Head + 采样入图）**：⚠️ 净收益约 0（TPOT -1.2%，噪声内），**不采纳**，但验证过程揭示了重要的性能认知
> - **优化3（W8A16 权重量化）**：✅ 达成预期，TPOT -15.9%，吞吐 +19%，HBM 反降 2GB，**采纳**（详见附录 E）
> - **优化1+优化3 叠加**：TPOT 累计 -27.2%（13.50→9.83ms），单卡吞吐累计 +37%（74.6→102.5 tok/s），HBM 几乎不变

## 1. 这阶段做了什么优化

### 1.1 优化目标

把 `nanovllm/layers/layernorm.py` 中**手写的 RMSNorm**（用 PyTorch 原语拼出，拆成 7 个小 kernel + 2 次 bf16↔fp32 cast）替换为寒武纪官方融合算子 **`torch_mlu_ops.fused_rms_norm`**（单个融合 kernel）。

这是 baseline 分析中排名第二的瓶颈（占 decode 单步 20.6%），也是第一优先级优化项。

### 1.2 为什么手写 RMSNorm 慢

原版 `rms_forward` 的实现（`layernorm.py`）：

```python
def rms_forward(self, x):
    orig_dtype = x.dtype
    x = x.float()                        # kernel 1: bf16→fp32 cast
    var = x.pow(2).mean(dim=-1, keepdim=True)  # kernel 2,3: pow + reduce
    x.mul_(torch.rsqrt(var + self.eps))  # kernel 4,5: rsqrt + mul
    x = x.to(orig_dtype).mul_(self.weight)    # kernel 6,7: fp32→bf16 cast + mul
    return x
```**慢的原因不是算子本身慢，而是**：
1. **kernel launch 数量爆炸**：每层 4 个 RMSNorm × 36 层 = **144 次/step**，每次拆 7 个小 kernel → ~580 个小 kernel + 288 次 cast
2. **bf16↔fp32 dtype 转换的 HBM round-trip**：每个小 kernel 都要把数据从 HBM 读出、计算、写回 HBM，cast 把数据在 HBM 间来回搬

profiler 实测：cast 0.92ms + reduce/rsqrt/mul 1.95ms = **2.87ms/step（20.6%）**。

### 1.3 优化方案

`fused_rms_norm` 把上述 7 个小 kernel 融合成 **1 个 kernel**，内部用高精度计算，无中间 HBM 往返。仅替换 MLU 路径，CUDA 路径保留原实现。

## 2. 具体修改了什么代码

### 2.1 原则：原版完全不动

所有修改放在新目录 `optimization_rmsnorm/`，原版 `nanovllm/layers/layernorm.py` **一行未改**。通过 monkey-patch 在运行时注入，便于 A/B 对比和随时回退。

### 2.2 核心修改：`rmsnorm_patch.py`

这是唯一的功能性改动。它 monkey-patch 了 `RMSNorm` 类的两个方法：

```python
# optimization_rmsnorm/rmsnorm_patch.py
import torch
from functools import lru_cache

@lru_cache(maxsize=1)
def _get_torch_mlu_ops():
    import torch_mlu_ops
    return torch_mlu_ops
    return torch_mlu_ops

def _is_mlu(tensor):
    return tensor is not None and tensor.device.type == "mlu"

_original_rms_forward = None
_original_add_rms_forward = None

def _patched_rms_forward(self, x):
    if _is_mlu(x):
        ops = _get_torch_mlu_ops()
        # 无 residual: store_output_before_norm=False
        return ops.fused_rms_norm(x, None, self.weight, None, None, self.eps, False)
    return _original_rms_forward(self, x)   # CUDA fallback

def _patched_add_rms_forward(self, x, residual):
    if _is_mlu(x):
        ops = _get_torch_mlu_ops()
        # 有 residual: store_output_before_norm=True, 返回 (normed, new_residual)
        return ops.fused_rms_norm(x, residual, self.weight, None, None, self.eps, True)
    return _original_add_rms_forward(self, x, residual)   # CUDA fallback

def apply_rmsnorm_patch():
    """在 import nanovllm 之后、构建 LLM 之前调用。"""
    global _original_rms_forward, _original_add_rms_forward
    from nanovllm.layers.layernorm import RMSNorm
    _original_rms_forward = RMSNorm.rms_forward        # 保存原方法
    _original_add_rms_forward = RMSNorm.add_rms_forward
    RMSNorm.rms_forward = _patched_rms_forward         # 替换
    RMSNorm.add_rms_forward = _patched_add_rms_forward
    return RMSNorm
```

### 2.3 `fused_rms_norm` API 映射（真机验证确认）

```
fused_rms_norm(x, residual, gamma, beta, bias, eps, store_output_before_norm, ...)
| 调用场景 | 参数 | 对应原方法 |
|---|---|---|
| `q_norm`/`k_norm`、首层 input_layernorm（无 residual） | `fused_rms_norm(x, None, weight, None, None, eps, False)` | `rms_forward` |
| `input_layernorm`/`post_attention_layernorm`（有 residual，Add+RMSNorm 融合） | `fused_rms_norm(x, residual, weight, None, None, eps, True)` | `add_rms_forward` |

关键参数 `store_output_before_norm=True`：返回 `(normed, new_residual)`，其中 `new_residual = (x + residual)` 转回原 dtype——与手写 `add_rms_forward` 语义**完全一致**（已验证 residual max_diff = 0.0）。

### 2.4 修改涉及的代码位置

| 文件 | 改动 | 说明 |
|---|---|---|
| `optimization_rmsnorm/rmsnorm_patch.py` | **新增** | 核心补丁，monkey-patch RMSNorm 方法 |
| `optimization_rmsnorm/layernorm.py` | **新增**（参考用） | 独立修改版，未实际使用（patch 方式更优） |
| `nanovllm/layers/layernorm.py` | **未改动** | 原版保留，patch 在运行时替换其方法 |
| `nanovllm/models/qwen3.py` | **未改动** | 调用 RMSNorm 的方式不变 |

### 2.5 遇到的两个坑（真机调试）
**坑 1：循环 import**
- 直接 `sys.modules` 注入修改版 `layernorm.py` 会触发 `nanovllm/__init__.py → qwen3.py → layernorm` 循环（注入时 RMSNorm 还没定义）
- **解决**：改用 monkey-patch 已加载的类方法，绕开模块加载顺序问题

**坑 2：`fused_rms_norm` 精度差异**
- bf16 输入下，fused 输出 vs 手写输出 max_diff = 3.12e-2（看似不一致）
- **深挖发现**：fused vs fp32 参考实现 = **0.0**，而手写 vs fp32 参考 = 3.12e-2
- **结论**：不是 fused 不准，而是手写的 `x.to(orig_dtype).mul_(weight)` 先转 bf16 再乘 weight 引入了额外截断误差。**fused 反而更精确**。差异在 bf16 正常量级（输出均值 0.64，相对 0.17%），端到端生成不受影响。

## 5. 总结

### 5.1 优化效果一句话

**用 1 个融合 kernel 替换 7 个手写小 kernel + 2 次 cast，RMSNorm 单算子加速 4.4x，端到端 TPOT 降 13.4%，batch=8 吞吐提升 20.4%，且 fused 算子比手写更精确。**

### 5.2 达成情况

| 目标 | 预期 | 实测 | 评价 |
|---|---|---|---|
| RMSNorm 降至 ~0.8ms/step | 0.8ms | 0.64ms | ✅ 超预期 |
| TPOT 降至 ~11.5ms | -15% | -13.4% (11.69ms) | ✅ 基本达标 |
| batch=8 吞吐 500→580 | +16% | +20.4% (594) | ✅ 超预期 |
| 正确性 | 无损 | fused 更准 | ✅ |
| Graph 模式 | 正常 | 正常 | ✅ |

### 5.3 额外发现

**TTFT 下降 32% 远超预期**——RMSNorm 在 prefill 阶段也占大头。原因是 prefill 时 token 数多（如 prompt=2048 有 2048 个 token），RMSNorm 按 token 维度计算，计算量随 token 数线性增长，融合收益被放大。这个收益在原 baseline 报告中未预估到。

### 5.4 HBM 代价

HBM 占用 +2.1GB（66.4 → 68.5GB），是 fused 算子内部 buffer 略增导致，80GB 卡还剩 ~10GB，可接受。

## 附录 B：优化2 —— Full Graph（LM Head + 采样入图）

在优化1 完成后，针对 decode 单步里 graph 外的固定开销（LM Head 0.70ms + 采样 0.24ms = 0.94ms，占 6.8%），我们尝试了第二个优化：把这些 graph 外的计算也纳入 MLU Graph capture。**结论是净收益约 0，不采纳**，但这个过程非常有学习价值。

### B.1 优化2 做了什么

原版是 **Partial Graph**：MLU Graph 只捕获 `self.model()`（embed + 36 层 + norm），而 LM Head（`compute_logits`）和采样（`sampler`）在 graph replay 之后单独执行：

```
graph 内:  model()  -> outputs[bs, hidden]        (graph.replay)
graph 外:  compute_logits(outputs) -> logits     (LM Head, 0.70ms)
           sampler(logits, temperatures) -> ids   (采样, 0.24ms)
           .tolist()                            (D2H)
```

优化2 改为 **Full Graph**：把 LM Head + softmax + 采样都放进 graph capture，graph 内直接输出采样后的 token id：

```
graph 内:  model() + compute_logits + softmax + random_sample -> sampled_ids[bs,1]
graph 外:  sampled_ids[:bs].view(-1).tolist()    (仅 D2H, 0.09ms)
```

### B.2 具体修改了什么代码

与优化1 同样，**原版 `model_runner.py` 一行未改**，新增 `optimization_fullgraph/fullgraph_patch.py`，monkey-patch `ModelRunner` 的三个方法（`capture_graph` / `run_model` / `run`）。核心改动是在 `capture_graph` 里把 graph 捕获范围从 `self.model(...)` 扩展到 `self.sampler(self.model.compute_logits(self.model(...)))`，并新增 `temperatures`、`sampled_ids` 两个 graph_vars。

| 文件 | 改动 | 说明 |
|---|---|---|
| `optimization_fullgraph/fullgraph_patch.py` | **新增** | patch 三个方法 |
| `nanovllm/engine/model_runner.py` | **未改动** | 原版保留 |

### B.3 优化2 的结果：净收益约 0

| 指标 | Before (Partial) | After (Full) | 变化 | 预期 |
|---|---|---|---|---|
| **TPOT** (b=1) | 13.51 ms | 13.61 ms | **+0.7%**（噪声） | -3~5% ❌ |
| **Device Idle** | 0.756 ms/step (2.8%) | 0.852 ms/step (3.2%) | **反增** | 降低 ❌ |
| **GEMM** | 7.98 ms/step | 7.97 ms/step | 不变 | — |
| **内存** | 66.4 GB | 66.8 GB | +0.4GB | — |
### B.4 为什么没收益（最重要的产出）

真机实测揭示了**之前性能估算的认知偏差**：

```
原版:  replay 12.55ms + graph外 0.98ms = 13.53ms
Full:  replay 13.27ms + graph外 0.09ms = 13.36ms
净收益: 0.17ms (-1.2%, 噪声内)
```

- graph 外开销从 0.98ms 降到 0.09ms（**省 0.89ms** ✅）
- 但 replay 从 12.55ms 升到 13.27ms（**多 0.72ms** ❌）——LM Head 的 0.614ms 真实 device 计算入图后仍在执行

**关键认知偏差**：之前把 graph 外 0.94ms wall-clock 全当可消除开销，但其中 **0.614ms 是 LM Head 真实 device 计算**（GEMV `[1,4096]×[4096,151936]`，入图不消失），只有 ~0.3ms 是可省的 launch 间隙。

**核心教训**：
- **算子融合（优化1）省的是真实 device 计算时间**（kernel 数量减少、HBM 往返减少）→ 收益实在（-13.4%）
- **入图（优化2）省的是 graph 外的 launch/sync 间隙**，但如果该 op 的 device time 本身就大（如 LM Head 0.614ms），入图后计算仍在，间隙又小，净收益被 graph 内开销抵消
- 入图有效的前提：graph 外 op 的 **launch 间隙占比高**（大量小 op），而非 device time 大

### B.5 优化2 踩的坑：`@torch.no_grad()` 缺失导致 OOM

patch 函数忘加 `@torch.no_grad()`，warmup 的 prefill（16384 tokens）保留 autograd 计算图，中间激活累积 60GB → OOM。原版 `run_model`/`capture_graph` 都有 `@torch.no_grad()` 装饰器。

**教训**：monkey-patch 类方法时，**必须保留原方法的装饰器**（`@torch.no_grad()`、`@staticmethod` 等），否则会引入难以察觉的副作用。

## 附录 C：学习专题 —— "增大 Graph 范围"具体是什么操作

优化2 的本质就是"增大 MLU Graph 的捕获范围"。这里把这个操作拆解成可学习的步骤，讲清楚它到底在做什么、为什么能省时间、以及什么时候有效。

### C.1 先理解 MLU Graph 在做什么

MLU Graph（和 CUDA Graph 类似）解决的是一个朴素的问题：**每执行一个算子，CPU 都要发一次指令给 MLU，这个"发指令"本身有开销**。

```
不用 Graph (Eager):
  CPU: 发指令1 ──等──> 发指令2 ──等──> 发指令3 ──等──> ...
  MLU:          执行1          执行2          执行3
  问题: CPU 发指令 + 等待 (launch + sync) 的开销, 在小算子上占比极高
```

Graph 的做法：**先把一串算子"录制"下来，之后每次只要"回放"整串，CPU 只发一次指令**：

```
用 Graph:
  录制阶段 (capture): CPU 跑一遍, 把算子序列记下来
  回放阶段 (replay):  CPU 发 1 次指令 ──────────────────>
            MLU:      执行1 → 执行2 → 执行3 → ... (连续, 无 CPU 介入)
  好处: 省掉了中间所有 CPU launch + sync 开销
```

这就是为什么 baseline 报告里 Eager 模式 TPOT 73-80ms，Graph 模式只有 13.5ms——Graph 消除了 82% 的 launch/sync 开销。

### C.2 "增大 Graph 范围"是什么意思

原版（Partial Graph）只把**模型主体**录进 graph，LM Head 和采样留在 graph 外：

```
┌─────────── graph.replay() ───────────┐    ┌── graph 外 ──┐
│ embed → 36层 → norm → outputs        │ →  │ LM Head → 采样│
└──────────────────────────────────────┘    └──────────────┘
        录制进 graph 的部分                      每步单独 launch
```

"增大范围"就是把右边那部分也录进 graph：

```
┌──────────────── graph.replay() ────────────────────────┐
│ embed → 36层 → norm → LM Head → softmax → 采样 → ids   │
└────────────────────────────────────────────────────────┘
                    全部录制进 graph
```

graph 外只剩一个 `.tolist()`（把采样得到的 token id 从 MLU 拷回 CPU，这个 D2H 拷贝无法入图，但只要 0.09ms）。
### C.3 具体操作步骤（对应代码改动）

**第 1 步：在 capture 时把更多算子包进录制块**

原版 `capture_graph` 里录制的是：
```python
with self.platform.graph_context(graph, self.graph_pool):
    outputs[:bs] = self.model(input_ids[:bs], positions[:bs])    # 只录 model()
```

增大范围后录制的是：
```python
with self.platform.graph_context(graph, self.graph_pool):
    logits = self.model.compute_logits(self.model(input_ids[:bs], positions[:bs]))  # +LM Head
    sampled = self.sampler(logits, temperatures[:bs])                              # +采样
    sampled_ids[:bs] = sampled.view(bs, 1)                                          # 存结果
```

就是把 `with graph_context` 块里的代码从"只调 model"扩展到"调 model + LM Head + 采样"。**graph 会把这块里遇到的所有 MLU 算子都录进去**。

**第 2 步：准备 graph 内需要的输入输出 tensor**

graph 是"录制-回放"模式，回放时输入必须用**同一块内存**（不能换新 tensor）。所以要预先分配固定的 buffer，每次回放前把新数据写进去：

```python
# 新增两个固定 buffer (原版只有 outputs)
temperatures = torch.ones(max_bs, dtype=torch.float32, device=self.device)  # 采样温度
sampled_ids   = torch.zeros(max_bs, 1, dtype=torch.int64, device=self.device) # 采样输出
```

回放前写入新输入：
```python
graph_vars["temperatures"][:bs] = temperatures    # 写入本次的温度
graph.replay()                                    # 回放, graph 内读这些 buffer
result = graph_vars["sampled_ids"][:bs]           # 从输出 buffer 读结果
```

**第 3 步：run_model 改为直接返回 token id**

原版 graph 回放后返回 hidden states，graph 外再做 LM Head：
```python
graph.replay()
return self.model.compute_logits(graph_vars["outputs"][:bs])   # graph 外做 LM Head
```

增大范围后 graph 内已经做完采样，直接返回 token id：
```python
graph.replay()
return graph_vars["sampled_ids"][:bs]   # graph 内已采样完, 直接返回 id
```

### C.4 这个操作的关键约束（学习要点）

1. **graph 内不能有依赖 Python 逻辑/动态 shape 的分支**：graph 录制的是固定的算子序列，回放时不能根据数据改变执行路径。所以 LM Head 在 decode 时不能走 prefill 的 `cu_seqlens_q` 分支——好在 decode 路径是固定的 `F.linear`，可以入图。

2. **输入输出必须用固定 buffer**：graph 回放时读写的内存地址必须和录制时一致，所以要用预分配的 `graph_vars`，每次写入新数据而不是创建新 tensor。

3. **随机性算子要单独验证**：采样是随机的，入图后要确认每次回放是否还产生不同结果（而不是被固定成录制时的值）。本例验证了 `random_sample` 入图后每次 replay 结果不同，随机性正常。

4. **内存会增大**：graph 内要持有中间 tensor（如 logits `[bs, 151936]`），bs 越大内存越大。本例 bs=16 时 logits 约 10MB，bs=512 时 300MB+ 会 OOM，所以做了 bs 分流（小 bs 用 Full Graph，大 bs 退回 Partial）。

5. **必须保留 `@torch.no_grad()`**：录制阶段如果保留 autograd，前向会存中间激活用于反向，内存爆炸。这是本优化踩的坑。

### C.5 什么时候"增大 graph 范围"有效（本优化的核心教训）

这是最值得记住的一点——**增大 graph 范围省的是"CPU launch/sync 间隙"，不是"MLU 计算时间"**。

判断一个 op 入图值不值，看它的 **wall-clock 时间里有多少是 launch 间隙、多少是真实 device 计算**：

```
op 的 wall-clock = device 计算时间 + CPU launch/sync 间隙
入图能省的  ≈  launch/sync 间隙        (device 计算入图后仍在做)
```

| 情况 | 举例 | 入图收益 |
|---|---|---|
| op device time 小、间隙大 | 大量微小 op（如手写 RMSNorm 的 7 个小 kernel） | **高**（省间隙） |
| op device time 大、间隙小 | LM Head（0.614ms 计算 + 0.06ms 间隙） | **低**（计算入图不消失） |

本例 LM Head 的 0.705ms wall-clock 里，0.614ms 是真实 GEMV 计算（入图后仍在），只有 0.06ms 是可省的间隙。所以入图后 graph 外省了 0.89ms，但 graph 内因为多了这些计算 replay 时间增加 0.72ms，净收益几乎为 0。

**对比优化1**：RMSNorm 融合是把 7 个小 kernel 变成 1 个，**直接减少了 device 计算时间**（2.84→0.64ms），这是"减少计算"，不是"挪位置"，所以收益实在。

**一句话总结**：
- 想省 **CPU 开销/launch 间隙** → 增大 graph 范围（有效当 op 多且小）
- 想省 **MLU 计算时间** → 算子融合/量化（有效当 op 计算量大）

## 附录 E：优化3 —— W8A16 权重量化
针对附录 D 指出的"GEMM 7.98ms 占 68%、memory-bound"这一绝对第一瓶颈，我们实施了优化3：把 Linear 层的 bf16 权重离线量化成 int8 + group-wise scale，推理时用 `torch_mlu_ops.scaled_matmul` 替换 `F.linear`，把权重读取量减半（bf16 2byte → int8 1byte），突破 decode 的 HBM 带宽墙。**结论：✅ 达成预期，TPOT -15.9%，吞吐 +19%，且 HBM 反降 2GB，采纳。**

### E.1 优化3 做了什么

decode（batch=1）的 GEMM 是 GEMV：`[1, K] × [K, N]`，算力极小，瓶颈是"把整个权重矩阵从 HBM 读到计算单元"。权重 bf16 时每个 GEMM 读 2 byte/元素；量化成 int8 后只读 1 byte/元素——**带宽需求减半，memory-bound 下 GEMM 直接加速**。这是优化1（算子融合省计算）之后的下一个抓手：优化1 省的是 RMSNorm 的计算时间，优化3 省的是 GEMM 的带宽时间。

整体流程（四步）：

```
第1步: 调研算子        第2步: 离线量化权重     第3步: 改推理代码     第4步: 验证
┌──────────┐         ┌──────────┐        ┌──────────┐      ┌──────────┐
│ 查 torch_mlu_ops │   ┌──▶│ 把 bf16 权重   │   ┌──▶│ F.linear →   │  ┌──▶│ 精度对比  │
│ 找到量化 GEMM    │   │  │ 转成 int8+scale │   │  │ scaled_matmul │  │  │ 性能对比  │
│ 看支持哪些格式   │──┘  │ 保存到内存       │──┘  │ 改 Linear 层   │──┘  │ 端到端测试 │
└──────────┘         └──────────┘        └──────────┘      └──────────┘
   (前期已做)           (一次性,离线)         (改代码)         (验证收益)
```

- **第1步（调研算子，前期已完成）**：`scaled_matmul(a, b, a_scale, b_scale, output_dtype, quant_bit_size, ...)`，`b` 的 shape 是 `(N, K)`——与 `F.linear` 权重布局 `(out, in)` **完全一致，无需转置**。group-wise 量化 `group_size ∈ [64,128,256,512,1024]`，per-channel 不支持。详见 memory `mlu590-weight-quant`。
- **第2步（离线量化）**：RTN group-128 量化，权重 int8 + 激活 bf16 不量化。
- **第3步（改推理代码）**：monkey-patch Linear 的 forward，MLU 路径用 `scaled_matmul`，CUDA 路径 fallback。
- **第4步（验证）**：精度 + 性能 + 端到端。

### E.2 量化方案：W8A16 group-wise RTN

```
权重 (N, K) bf16  ──沿 K 维按 group_size=128 分组──▶  (N, K//128, 128)
每组: scale = max(|w_group|) / 127
      w_int8 = round(w_group / scale).clamp(-127, 127)   # RTN, Round-To-Nearest
反量化: w ≈ w_int8 * scale   (scaled_matmul 内部完成)
```
- **W8A16**：权重 int8（W8），激活 bf16 不量化（A16）。`a_scale=None, a_quant_bit_size=-1`。
- **group-128 而非 per-channel**：MLU590 的 `scaled_matmul` group-wise 量化 `group_size` 只支持 `[64,128,256,512,1024]`，per-channel（K=4096）不支持。group-128 精度足够。
- **RTN**：最简单的量化算法（无需校准数据），真机实测相对误差 0.66%，对 LLM 推理可忽略。

### E.3 关键决策：只量化大 GEMM，跳过 o_proj

真机实测（memory `mlu590-weight-quant`）：`scaled_matmul` 的加速取决于 GEMM 规模——大 GEMM 带宽收益 > 量化开销（加速 1.4x），小 GEMM 量化开销 > 带宽收益（反而变慢 0.78x）。所以**只量化大 GEMM，跳过小 GEMM**：

| Linear 层 | 权重 shape | bf16 显存/全模型 | 是否量化 | 原因 |
|---|---|---|---|---|
| `gate_up_proj` | (24576, 4096) | 6912 MB | ✅ 量化 | 最大 GEMM，带宽收益最大 |
| `down_proj` | (4096, 12288) | 3456 MB | ✅ 量化 | 大 GEMM |
| `qkv_proj` | (6144, 4096) | 1728 MB | ✅ 量化 | 中大 GEMM |
| `o_proj` | (4096, 4096) | 1152 MB | ❌ 跳过 | 小 GEMM，量化反而变慢 0.78x |

量化 108 个 Linear（36 层 × 3），跳过 36 个（36 层 × o_proj）。量化部分 bf16 11.81GB → int8+scale 6.23GB，**省 5.91GB 权重显存**。

### E.4 具体修改了什么代码

与优化1/优化2 同样，**原版 `linear.py`、`loader.py`、`model_runner.py` 一行未改**，全部放在新目录 `optimization_w8a16/`，通过 monkey-patch 注入。

**核心补丁 `w8a16_patch.py`** 的三个关键函数：

```python
# 第2步: RTN group-wise 量化 (bf16 权重 -> int8 + scale)
def quantize_weight_rtn_mlu(weight, group_size=128):
    N, K = weight.shape
    group_num = K // group_size
    w = weight.float().view(N, group_num, group_size)
    amax = w.abs().amax(dim=-1, keepdim=True).clamp(min=1e-8)
    scale = amax / 127.0
    w_int8 = torch.round(w / scale).clamp(-127, 127).to(torch.int8).view(N, K)
    return w_int8, scale.view(N, group_num)   # (N,K) int8 + (N,group_num) fp32
# 第3步: scaled_matmul 替换 F.linear (b 布局与 F.linear 权重一致, 无需转置)
def scaled_matmul_linear(x, w_int8, w_scale, bias):
    return ops.scaled_matmul(x, w_int8, None, w_scale, x.dtype,
                             bias=bias, quant_bit_size=8,
                             a_quant_bit_size=-1, act_mode="none")  # (M,K)×(N,K)->(M,N)

# 一键注入: monkey-patch load_model, 加载后自动量化目标 Linear
def apply_w8a16_patch():
    _original_load_model = loader_mod.load_model
    def _patched_load_model(model, path):
        _original_load_model(model, path)          # 先加载 bf16 权重
        apply_w8a16_to_model(model, ...)            # 再在内存中量化
    loader_mod.load_model = _patched_load_model     # 原版 model_runner 一行不改
```

**`apply_w8a16_to_model`** 遍历模型，对目标 Linear：RTN 量化 → 把 `self.weight`（bf16 Parameter）替换成 `w_int8`（int8 buffer）+ 注册 `w_scale`（fp32 buffer）→ 实例级 patch `forward` 用 `scaled_matmul_linear`。非目标 Linear（o_proj）保持原 `F.linear`。RowParallelLinear 的 `all_reduce` 语义保留。

| 文件 | 改动 | 说明 |
|---|---|---|
| `optimization_w8a16/w8a16_patch.py` | **新增** | 量化函数 + Linear patch + load_model patch |
| `optimization_w8a16/quantize_weights.py` | **新增** | 第2步离线量化真机演示 |
| `optimization_w8a16/baseline_optimized.py` | **新增** | 优化1+优化3 叠加性能测试 |
| `optimization_w8a16/test_correctness.py` | **新增** | 端到端正确性 |

| `optimization_w8a16/profile_w8a16.py` | **新增** | kernel 级 GEMM 耗时对比 |
| `nanovllm/layers/linear.py` | **未改动** | 原版保留 |

MLUMatMulGepm (bf16 GEMV, 剩余)      24.28ms (666次)   ← 仅剩 o_proj + LM head (未量化)
GEMM 合计                            109.44ms          6.08 ms/step  (-23.6%)
MLUFuseNorm (RMSNorm)                11.68ms           0.65 ms/step  (不变)
MLUSingleQueryCachedKVAttn           10.11ms           0.56 ms/step  (不变)
```

**关键证据**：bf16 的 `MLUMatMulGepm` 从 143.26ms 降到 24.28ms（只剩未量化的 o_proj + LM head），被 int8 的 `MLULLMQuantMatmulNXK`（85.16ms）替换。GEMM 总 device time **7.96 → 6.08 ms/step（-23.6%）**——这就是权重量化减半带宽在 kernel 级的直接体现，也是 TPOT -15.9% 的来源。RMSNorm、Attention 不受影响（量化只动权重）。
### E.7 HBM 反降 2GB（额外收益）

优化1 时 HBM 68.51GB，优化3 后 **66.48GB（反降 2.03GB）**。原因：bf16 权重（11.81GB 量化部分）→ int8+scale（6.23GB），**省 5.91GB 权重显存**；虽然 graph capture 等额外占用略增，但净效果是 HBM 下降 2GB。这和优化1（fused 算子内部 buffer 略增导致 +2GB）正好相反——优化3 不仅降延迟，还省显存，**为开更大 batch / 更长上下文腾出空间**。

### E.8 三个优化的对比与叠加效果

| | 优化1（RMSNorm 融合） | 优化2（Full Graph 入图） | 优化3（W8A16 权重量化） |
|---|---|---|---|
| 优化手段 | 算子融合（7→1 kernel） | 计算位置转移（graph 外→内） | 权重量化（bf16→int8） |
| 省的是什么 | **RMSNorm 计算时间** | **launch/sync 间隙** | **GEMM 权重读取带宽** |
| 作用于瓶颈 | RMSNorm（原 21%） | graph 外 0.94ms（6.8%） | GEMM（68%，绝对第一） |
| 净 TPOT 收益 | **-13.4%** | -1.2%（噪声） | **-15.9%** |
| HBM | +2.1GB | +0.4GB | **-2.0GB** |
| 采纳？ | ✅ 采纳 | ❌ 不采纳 | ✅ 采纳 |

**叠加效果（baseline → 优化1+优化3）**：

| 指标 | baseline | 优化1 | 优化1+优化3 | 累计 |
|---|---|---|---|---|
| TPOT (b=1,p=128) | 13.50 ms | 11.69 ms (-13.4%) | 9.83 ms (-15.9%) | **-27.2%** |
| Out tok/s (b=1) | 74.58 | 85.93 (+15.2%) | 102.53 (+19.3%) | **+37.4%** |
| batch=8 吞吐 | 493 tok/s | 594 (+20.4%) | 662.6 (+11.5%) | **+34.4%** |

两个有效优化（1 和 3）叠加：**TPOT 累计降 27.2%（13.50→9.83ms），单卡吞吐累计提升 37%（74.6→102.5 tok/s），且 HBM 占用几乎不变**。优化1 的 +2GB 被 优化3 的 -2GB 抵消，最终 HBM 与 baseline 持平——这意味着**优化1+优化3 在不增加显存代价的前提下，把 decode 延速降了四分之一多**。

### E.9 为什么权重量化有效（核心认知）
优化3 的成功再次印证了附录 D 的核心结论，并补充了一个新维度：

```
decode (batch=1) 是 memory-bound: 算力极小, 瓶颈是"读权重"
  bf16 权重: 每个 GEMM 读 2 byte/元素  →  GEMM 7.96ms/step (68%)
  int8 权重: 每个 GEMM 读 1 byte/元素  →  GEMM 6.08ms/step (62%)
  带宽减半 → memory-bound 下 device time 直接下降 23.6%
```

**对比三个优化省的东西**：
- 优化1（融合）省 **RMSNorm 的计算时间**（kernel 数减少、HBM 往返减少）→ 真实 device time 减少
- 优化2（入图）省 **launch/sync 间隙**（但 device time 大的 op 入图后计算仍在）→ 被抵消
- 优化3（量化）省 **GEMM 的权重读取带宽**（int8 比 bf16 少读一半）→ 真实 device time 减少

**一句话**：优化1 和 优化3 都成功，因为它们都**直接减少了真实 device time**（一个减计算、一个减带宽）；优化2 失败，因为它只挪位置不减计算。而优化3 比 优化1 更进一步——它针对的是占比 68% 的绝对第一瓶颈 GEMM，且 decode 的 memory-bound 特性让"减带宽"这个手段发挥到极致。

### E.12 下一步

优化1+优化3 后 decode 单步（9.83ms）瓶颈分布：
```
GEMM        6.08ms  62%   ← 仍是第一瓶颈, 但已从 7.96ms 降下来
RMSNorm     0.65ms   7%   ← 优化1 已优化
Attention   0.56ms   6%
其他        ~2.54ms  26%
```

GEMM 仍是第一瓶颈，但权重量化已把它的 device time 压到接近 memory-bound 下限（int8 已是 W8，再降需 W4 但需 GPTQ 保精度）。后续可考虑：
- **W4A16（需 GPTQ）**：权重再减半（int8→int4），但 RTN 精度差（11.7%），需 GPTQ/AWQ 校准降至 <2%，工程量大。
- **KV cache 量化**：作用于 Attention（6%），对 TPOT 影响小，但能省 KV 显存开更大 batch（与优化3 省 weight 显存叠加，进一步升吞吐）。
- **batch 维度优化**：优化3 在大 batch 收益稀释（-15.9%→-11.4%），可探索 batch 调度策略。

当前单卡 batch=8 吞吐已达 662 tok/s（baseline 493），累计提升 34%，且 HBM 不增——优化1+优化3 是一组互补且都有效的优化组合。

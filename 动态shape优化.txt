基于“skill 只定约束、方法层留白”的现状，和本次 softmax 任务暴露的五个实测病灶，给出分层的改进建议。每条都注明：改哪份文档、补什么规则、实证依据是什么。

  一、方法层补白（改 share/shape/README.md，最高优先级）

  skill 的桶规则是“边界约束”缺“方法指导”，这是所有病灶的根源。建议在 README 分桶相关章节补四条规范性方法（不是强制算法，是默认方法 + 偏离需说明）：

  1. 桶轴选择规则：“归约轴分桶、并行轴也必须评估”

  现状问题：README 只说“用 shape-aware autotune keys”，没说 key 该放哪些轴。本任务执行时把 N（归约轴）当 key、M 完全不进 key，无人质疑——而 M-sweep 实测证明这是 128/256 桶 0.06x 灾难的直接原因。

  建议补规则：

  ▎ 桶 key 的轴选择必须做“轴敏感性分析”：对每个运行时轴，固定其他轴扫描该轴（至少 3 个采样点：下界/中点/上界附近），若最优配置随该轴变化（任两点最优 config 不同），该轴必须进入桶 key
  ▎ 或在配置内参数化；分析结论写入优化报告。单维桶只有在证明第二维不敏感时才允许。

  实证依据：M=64 时 N=192 桶 1.67x（BM1 无妨），M=8192 时 0.06x（BM1 致命）——M 对最优 BLOCK_M 明显敏感，却被结构性忽略。同类形态在 64 桶（BM32）能到 0.56x~1.06x，证明敏感性是真实的、可修复的。

  2. 桶内代表覆盖规则：“桶内调参样本必须覆盖桶 key 的两个极端”

  现状问题：gen-autotune-config 固化了“桶内非 holdout case 中位数之和”选优，但没要求桶内 case 的 key 维度取值要拉开。256 桶只有 M=1 的用例 → 配置退化。

建议补规则：
 ▎ 每桶进入调参的 case 集合必须至少包含“桶 key 维度取桶内最小值”和“取桶内最大值”的各一个非 holdout case（M 进 key 时即小 M 和大 M 各一；否则须证明 M
  ▎ 不影响该桶配置）。冻结套件生成时，套件生成器应自动为每个桶补入这两个锚点 case。

  落点：这条同时要改 shape_runtime.py 的 generate_suite——让套件生成器感知桶结构，自动补桶极值锚点。这是把“桶内代表性”从碰运气变成机制保证。

  3. 桶内选优判据：从中位数之和改为 maximin

  现状问题：“中位数之和”会为桶代表 shape 的峰值牺牲桶内其他成员。config-tuner 第 4 轮已经手工做了正确决策（BM64 峰值快 3% 但伤小 M 1.67x → 弃，选 BM32），说明执行者凭直觉在补这个洞，但规则没写。

  建议补规则：

  ▎ 桶内配置选优判据改为：maximize min(case_speedup)，即最大化桶内最差 case 的加速比；并要求报告每桶的“桶内最差/最好 case 加速比”两个数字。平均值仅作 tie-break。

  落点：改 gen-autotune-config 和 config-tuner 两份 strategy.md 的 Step 4/Step 3。

  4. 桶粒度与掩码浪费率规则

  现状问题：next_power_of_2(N) 分桶让 4096 桶的 N=2176 承受 47% 的 BLOCK_N 掩码浪费（实测 0.53x），桶粒度合适与否无规则可依。

  建议补规则：

  ▎ 桶设计时必须计算桶内最坏掩码浪费率 (BLOCK_N - N_min_in_bucket)/BLOCK_N；超过 25% 时必须：a) 细分桶（但仍受 ≤16 上限），或 b) 采用列分段循环（kernel 内 for start in range(0, N,
  ▎ BLOCK_N)，块数作为运行时参数），让 BLOCK_N 与实际 N 解耦。b 是默认选项，因为它对任意粒度统一生效。

  实证依据：浪费率 > 25% 的 shape 全部输（192→0.09x、320→0.62x、1216→0.62x、2176→0.53x），≤2% 的全部赢或持平（4032→1.08x、4096→1.07x）——25% 就是实测的分界线。且官方示例 dynamic_reduce_kernel.py
  本身就是列分段循环写法，规则只是把示例行为升格为强制。
   二、协议层改进（改 main/optimize 的 SKILL.md）

  5. 性能基线规则：“必须对比官方融合算子”

  现状问题：本次工作流以手写 eager 5 算子分解为 torch 基线，得出“6.42x 加速”的结论；换官方 F.softmax 对比只有 1.03x（冻结口径）/ 0.84x（全域口径）。加速比数字差 6 倍，而 summary.md 无任何提示。

  建议补规则：

  ▎ torch 基线优先使用官方融合算子（torch.nn.functional. / torch.* 中的单算子入口）；只有目标算子无官方实现时才允许 eager 分解，且 summary 中必须注明“基线为非融合 eager 分解”。summary
  ▎ 的加速比字段旁必须给出对照基线的实现形态。*

  6. 性能汇报规则：“禁止单一均值，必须分档且分档穷尽”

  现状问题：我自己就先后犯过两个错——只报 8 case 均值（掩盖桶级灾难），分档不穷尽（大/小两组都高于总均值，中间 22 个样本被漏掉）。这类误导在 summary.md 的固定模板下很容易发生。

  建议补规则：

  ▎ summary 的性能对比除总均值外，必须给出“按数据规模分档”的表格，且分档必须穷尽全部 benchmark case（不允许留空洞档位）；必须列出最差 N 个 case（建议 N=5）的逐 case 数字。动态 shape
  ▎ 任务还必须给出按桶的加速比表格——桶是配置的选择单位，桶级表现才是优化质量的直接度量。

  实证依据：8 case 均值 1.03x 看起来“略胜”，桶级表格会立刻暴露 256 桶 0.09x；这正是 skill 要求“summary 明确分桶”的初衷，但现有模板没有把桶级性能数字落实成必填项。
   7. 调参信号源规则：“perf-analyzer 的信号覆盖声明”

  现状问题：优化器以 8 个 benchmark case 为唯一性能信号源，128/256 桶在信号里“不存在”，no_applicable_advanced_strategy 自然停止时，盲区永远不会被发现。预算没用完（7/16
  subagent）也帮不上——不是资源问题，是可见性问题。

  建议补规则：

  ▎ perf-analyzer 每轮必须输出“信号覆盖声明”：列出每个桶在 benchmark case 中的样本数；样本数为 0 的桶标记为“性能未知”，这些桶不允许声称“已优化”，且 summary 的“未覆盖范围”章节必须逐桶披露（现在只披露
  ▎ shape 未覆盖，不披露“桶无性能证据”）。

  落点：改 perf-analyzer/strategy.md 和 summary 模板。这与 skill 现有措辞“summary 明确……分桶”一致，是把它做实。

  三、执行层工具改进（改 strategy.md / 脚本）

  8. gen-autotune-config：key 设计从“轴列表”升级为“轴 + 桶边界设计”

  现有 Step 2.3 只说“key 使用轴列表”。建议拆成两个子步骤：
  - 2.3a key 轴选择：引用上面第 1 条的敏感性分析；
  - 2.3b 桶边界设计：对进 key 的轴，桶边界默认用“利用率等分”（如 N 轴按 ceil(2^k×0.75) 检查浪费率）而非机械 next_power_of_2；并在文档中给出“允许双维 key（如 (N桶， M密度桶)），桶总数仍受 ≤16
    约束”的明确许可——现在 README 的 1~16 上限写的是 SHAPE_DISPATCH 分支数，双维 key 是否合法没有明说，执行者倾向于保守单维。

  9. config-tuner：M 扫描纳入标准动作

  config-tuner 现在只看 NRAM 利用率信号。建议把“桶 key 之外的主并行轴 M 扫描（64/512/2048/8192 四点）”列为 config-tuner 的固定验证步骤——每桶配置改动后必须在这四点上复核零回归，而不只测桶代表
  shape。本任务 BM32 的 tie-break 实际上做了单桶单点复核，把它机制化为全桶四点。

10. holdout 的性能条款（可选项，供权衡）

  holdout 现在只验精度、不验性能，导致“配置对没见过的 shape 性能崩了”完全无告警。不建议让 holdout 进性能判定（会破坏“调参不可见”的隔离原则），但可以加一条折中：finalize 后对 holdout
  做一次“性能体检”——只测不判，数字写进 summary 的“未覆盖范围”章节作参考。这样 256 桶盲区至少会在交付物里留下可追的线索，又不污染调参隔离。

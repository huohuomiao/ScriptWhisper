（MLU Triton）

  〇、总体架构

  方案要求：由 4 个 Skill 分层编排——mlu-triton-main（主控）+ mlu-triton-code-gen（代码生成）+ mlu-triton-code-review（执行/修复/验证）+ mlu-triton-optimize（性能优化）。主流程通过 run_control.py
  状态机管理 5 个外层阶段：

  init → env_config → extractor → kernel_gen → optimizer → finalize → done

  每阶段受三个机制保护：内容指纹与产物 SHA-256（失效向下游传播）、内容寻址缓存（.mlu-triton-cache/，断点续跑）、L1/L2/L3 验证等级（L1 结构校验、L2 schema 校验、L3 真实 MLU 执行证据）。主流程是
  run_manifest.json 的唯一写入者；subagent 任务阻塞串行、禁止并发。

  真实做了：两次运行都全新执行（无缓存恢复），每阶段 attempts=1，manifest 事件序列完全对应上述 DAG；两次都出现 fingerprint_changed 失效事件（env_config/extractor
  完成后正常刷新下游指纹），无失败重试、无 not_comparable 记录。

  一、初始化（run_control init）

  需要做什么：
  - 识别任务类型 static / enumerated / dynamic（动态 shape 任务必须走 shape 协议）；
  - 运行 run_control.py init --output-dir <dir> --input <需求文件或文本> --mode <optimization_mode>，确定 optimization_mode（correctness / balanced / max-performance）；
  - 用户提供了契约文件时附加 --shape-contract；
  - 不得用样例 shape 推断整个支持域；要求动态但未给范围时先补齐边界；
  - 清单已存在时禁止再 init，必须 resume。

  真实做了：两次都是 kind=literal 内联需求文本 + mode=max-performance，budget_file=null（未显式提供预算，使用 max-performance 模式默认值：wall 7200s / subagent 16 / worker 16 / strategy 12 /
  advanced 3 / patience 2 / min_improvement 2%）。动态 rank、数据依赖输出长度、零维度大小被明确划出支持范围。

  二、阶段 1：EnvConfig 环境准备与验证

  需要做什么：
  - 先跑 next 确认 env_config/run，再 start；
  - 强制顺序：本地依次执行 get_device_info.py 和 test_env_code.py，两者 exit 0 → execution_backend=local；任一失败则向远端 Worker 提交同一套检查（阻塞前台），都失败则停止并报告真实 stdout/stderr；
  - 本阶段由 subagent 执行（禁止主流程接管）；永不从缓存恢复，每次运行重新确认设备；
  - 产出 3 个产物：config.md（环境报告）、runtime_info.txt（检查输出原文）、run_context.json（稳定的 hardware_key / toolchain_key），随后 bind-context 绑定上下文。

  真实做了：两次均本地通过、判定 execution_backend=local（MLU590-M9DG，NeuWare 4.6.2 / Triton 3.2.0 / torch_mlu 1.31.1 + torch 2.9.1），未使用 Worker。差异在于 hardware_key 记录口径：softmax 记为
  MLU590-M9DG:1x81920MiB:FULL，RmsNorm 记为 MLU590-M9DG:1:80GiB:fw_v1.1.1:driver_v6.5.26——同一块卡的两次运行指纹表述不同，是跨 run 不可直接比绝对毫秒的一个原因。

  - 契约与用例一经冻结即带 hash（shape_contract_hash / test_suite_hash），后续所有阶段不得改动；
  - 缓存要求 L1+L2。

  四、阶段 3：KernelGen 代码生成（三组 checkpoint）

  需要做什么——mlu-triton-code-gen Skill 按 normal（DesignKernel → BuildKernel → Code Review 两代理链）或 triton_fast（跳过设计）路由，分三组 checkpoint 落盘，每组要求相应验证等级后才可
  checkpoint-save：

  ① design 组（Step 1–4，仅 normal 路由，L1+L2）：
   - Step1 step1_base_info.json：算子名、计算公式、torch 参考实现、IO 轴/dtype/stride、归约轴、符号域（与契约 hash 绑定）；
  - Step1 step1_io_shapes.json：IO 形状明细；
  - Step2 step2_block_mapping.json：逻辑轴 → block 参数映射（PARALLEL 轴挂 BLOCK_M，REDUCE 轴挂 BLOCK_N）；
  - Step3 step3_axis_fusion.json：逐对检查相邻轴能否融合，归约边界/动态语义边界禁止融合，须给出明确理由；
  - Step4 step4_code_spec.json：kernel 代码规格。
  - 允许同上下文内 1 次自修复，再失败则停止、不得启动 Build。

  ② build 组（Step 5–6，L1+L2）：
  - Step5 step5_kernel_code.py：kernel + wrapper；
  - Step6 step6_test_code.py：完整测试代码（输入构造、PyTorch 参考、torch.allclose、triton.testing.do_bench），只生成不执行；
  - 要求 Step6 保持 Step5 的 kernel/wrapper、不得伪造任何精度/性能结果。

  ③ review 组（Step 7，L1+L2+L3）——由主流程直接调 mlu-triton-code-review Skill（不进 subagent）：
  - Code Review 拥有全部真实执行权：读取 EnvConfig 固定后端，真实 MLU 上跑全套件；
  - 直接通过（零 agent）→ status=passed；业务失败（精度/执行错误）→ 分发 ReviewAndFix subagent 做保守最小修复（契约：step6_test_code.py →
    step6_test_code_fix.py），修复后全量重跑；基础设施错误不得触发代码修复、不得产生可复用 checkpoint；
  - 产物：step6_test_code_fix.py/.md、review_result.json（v2 schema：status / validation_level=l3 / accuracy.pass / 全部 expected_case_ids / code_hash / suite_hash）；
  - 通过后复制为 triton_code_fix.py（👉 Optimizer 输入）、triton_report.md、dispatch_metrics.json。

  真实做了：

  - softmax：走 normal 路由（not_triton 输入），DesignKernel 产出 5 个 JSON。Step3 轴融合分析结论：M/N 不融合——N 是 dim=-1 归约轴，融合会破坏行边界语义和 row < M 掩码。Review
    直接通过（status=passed，attempts=1，60/60 case + 3 A-B-A + 13 guard，max_diff=8.94e-08）。基线性能：Triton 2.9276 ms vs PyTorch 0.3189 ms（0.11x，初始版本反而慢 9 倍）。
  - RmsNorm：同样 normal 路由。Review 首轮失败——step6_initial_failure.log 记录 import ast 缺失导致 NameError，触发 ReviewAndFix 最小修复 1 轮，全量重跑后通过（status=repaired，attempts=2，54/54 +
    A-B-A 3/3 + guard 15/15，max_diff=9.5e-07）。基线：Triton 0.3028 ms vs PyTorch 0.0832 ms（0.27x）。

 这一步是全流程中“方案分支”最清晰的体现：同一个 review 阶段，softmax 走了零 agent 直接通过路径，RmsNorm 走了 1 轮修复路径，两者的 review_result.json（status=passed vs repaired）就是 L3 证据。

  五、阶段 4：Optimizer 性能优化

  需要做什么——mlu-triton-optimize Skill，五步流程，一切动作受同一状态文件预算硬约束：

  步骤 1 输入检查：确认输入含 @triton.jit kernel、launch、wrapper、精度测试、性能测试，缺一即停。

  步骤 2 生成计划：运行 optimization_control.py plan，产出 optimization_plan.json（模式、静态信号、策略路由、预算）+
  optimization_state.json（用量、最佳候选、patience、历史）。信号来自对代码的静态分析：有无归约、grid 维度、block 参数、autotune、除法、libdevice 候选等，据此静态路由 5 个 OOB 策略，只执行
  selected=true 的。已存在 plan/state 时必须 --resume，禁止重建状态绕过预算。

  步骤 3 OOB 策略串行执行（每策略：预算 check → 建目录 {n}_{策略}/、上一轮通过精度的代码复制为 input.py → record subagent → 分发 Optimizer subagent 只做该策略 → 校验产物 → 从报告取
  accuracy_pass/original_ms/opt_ms → record strategy；精度不过的候选不得成为下一轮输入）：
  1. retiling——分块重铺：block_size 全覆盖检查（每个逻辑轴必须有 block 参数且有效参与张量构建）、归约轴规范化；
  2. reduce-opt——归约优化；
  3. modify-grid——grid 展平/物理核封顶；
  4. index-computation-simplify——无整除/取模则跳过；
  5. gen-autotune-config——可调 constexpr 分块参数的 autotune/分桶固化。

  OOB 完成后最近通过精度的候选 → triton_oob_optimized.py。

  步骤 4 advanced 深度优化（仅 max-performance）：每轮 = 预算 check → perf-analyzer subagent 性能分析 → 分析建议与候选池（libdevice-opt / config-tuner / div-to-mul）取交集，空则
  no_applicable_advanced_strategy 停止 → 执行一个候选 → 精度+性能实测 → 提升达 min_improvement_pct 才重置 patience，否则回退。产物 triton_advanced_optimized.py。

步骤 5 最终选择与报告：选择顺序 = state.best（valid）→ advanced 赢家 → OOB 赢家 → 原始输入；复制为 triton_optimized.py + triton_optimized.md；每个精度通过的候选都存入 Optimizer/verified/（代码
  hash-结果 hash 双文件证据）。

  需要做什么（本阶段不缓存，确保总结反映真实恢复路径）：

  七、贯穿全程的动态 shape 专项机制

  这部分是“动态 shape 算子开发”区别于静态算子开发的核心，两次运行均已落实：

  1. wrapper 全域 guard：每次调用检查 rank/dtype/设备/contiguous/域边界（softmax 13 项 guard、RmsNorm 15 项），域外输入显式拒绝而非静默转连续——负向 guard 测试是冻结套件的一部分；
  2. 静态分桶调度（SHAPE_DISPATCH / FROZEN_CONFIGS）：按 N 桶固化 BLOCK 参数字面量，任意运行时 (M,N) 命中固定桶配置，无运行时 autotune 搜索（避免线上抖动），每个桶有无条件兜底；
  3. holdout 隔离：3 个 holdout case 不参与调参只做验证，防止策略过拟合；
  4. A-B-A 序列测试：3 组同 shape 重复调用验证无跨调用状态污染；
  5. 证据链防伪：契约 hash → 套件 hash → 代码 hash → 结果 hash 层层绑定，verified/ 中每个候选都有代码+结果双 hash 文件，summary 缺数据必须显式 N/A（原因）；
  6. 支持域声明：summary 明确“已测用例是有界证据，非全域证明”，动态 rank、零维、数据依赖输出长度不在支持范围。

  八、两次运行的流程一致性结论

  同一套 skill（两个项目的 .claude/skills 字节级一致）驱动，两个算子产出了逐阶段对齐的目录结构（EnvConfig/ Extractor/ KernelGen/ Optimizer/ verified/ triton_final.py/ summary.md/
  regression_result.json）。流程上的差异全部是“按需触发的分支”，而非步骤不同：ReviewAndFix 修复分支（RmsNorm 触发、softmax 未触发）、retiling 适用性分支（RmsNorm 改造、softmax 判定不适用）、advanced
  迭代深度（softmax 2 轮、RmsNorm 0 轮即被 PMU 证据说服停止）。这验证了方案的核心设计：策略由静态信号路由、停止由预算和真实证据决定、每个结论都有 hash 绑定的 L3 证据。
